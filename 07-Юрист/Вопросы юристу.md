Рабочий список тем для согласования с профильным юристом (152-ФЗ, договорное право, границы ответственности сервиса).  
**Не юридическая консультация.** Ответы фиксируем здесь или в итоговых текстах документов; закрытые пункты можно помечать датой и ссылкой на редакцию.

## Акцепт и интерфейс регистрации

1. **Одна галка на весь комплект документов.** Допустимо ли при регистрации показывать **список ссылок** на политику конфиденциальности, пользовательское соглашение и согласие на ПДн (и иные обязательные тексты) и **одну** отметку «принимаю / ознакомлен со всем перечисленным», без отдельной галки на каждый документ? Нужны ли исключения (см. п. 2–3 ниже)?

   **Решение v1.0 (2026-05-24):** одна галка на три документа + отдельные ссылки на тексты; реализация — `RegisterPage.vue`. **На юриста v2.0:** подтвердить допустимость единого акцепта.

2. **Чувствительные / специальные категории ПДн.** **Решение директора (2026-05-26):** отдельный экран при первом входе в «Дневник» / «Прогресс»; текст — [Согласие на обработку медицинских данных v1.0](./Согласие%20на%20обработку%20медицинских%20данных%20v1.0%20—%20черновик.md).

   **Ответ ревью (2026-05-24):** [Ревью — согласие медицинские ПДн v1.0 (2026-05-24).md](./Ревью%20—%20согласие%20медицинские%20ПДн%20v1.0%20(2026-05-24).md)

   | Подвопрос | Вывод |
   |-----------|--------|
   | Отдельный экран vs один акцепт при регистрации | **Отдельный экран — верно** (ст. 10 ч. 2 п. 1) |
   | Квалификация данных (ст. 10) | Замеры, питание, сон — **да**; шаги/вода — **спорно**, **оставляем в согласии** (консервативно) |
   | Письменная форма + кнопка «Даю своё согласие» | **Допустимо** как ст. 9 ч. 2 п. 3 при фиксации user_id, редакции, времени, IP, UA, **device_id** ([T-011](../backlog/сделано/T-011-legal-acceptances-audit-поля.md)) |
   | Чекбокс «Ознакомлен(а)» + кнопка | **Рекомендовано** (внесено в §7.3 согласия и T-010) |

   **Остаётся у внешнего юриста (опционально):** узкая квалификация шагов/воды; SMS-подтверждение; срок хранения записей об акцепте.

3. **Дисклеймер «сервис не является медицинским»** (`medical_disclaimer`).

   **Вопросы юристу (v2.0):**
   - Достаточно ли для пилота **без отдельного акцепта**: строка в footer public, формулировки в ПС/политике и явный пункт в мед. согласии Client («сервис не оказывает мед. услуг»)?
   - Нужен ли **отдельный** документ с публичной страницей `/legal/medical-disclaimer`?
   - Нужен ли **отдельный экран** или отметка (не при регистрации): только Client, только Pro, оба, другой момент (например первая выдача плана)?
   - Нужна ли **запись в `legal_acceptances`** или достаточно информационного показа?

   **Решение v1.0 (2026-05-24) — принимаем как есть, без изменений до v2.0:**

   | Элемент | Статус v1.0 |
   |---------|-------------|
   | Отдельный акцепт `medical_disclaimer` | **Нет** |
   | Footer public (`telotron-public-footer`) | **Да** — «сервис не медицинский…» |
   | Мед. согласие Client | **Да** — в тексте и чекбоксе |
   | Ключ `medical_disclaimer` в `legal_documents` | Stub в seeder, **не** в обязательном комплекте |
   | Публичная страница `/legal/medical-disclaimer` | **Не** подключена (ссылка в мед. согласии — на будущее) |
   | Pro | Отдельного показа **нет** (тренер не вводит мед. данные клиента в продукте) |

   Канон акцептов: [Схема юрдокументов и этапы акцепта (Pro · Client).md](./Схема%20юрдокументов%20и%20этапы%20акцепта%20(Pro%20·%20Client).md).

22. **Обязательный ключ входа (Passkey) для тренера (Pro).** Рег. шаг 3: тренер **обязан** привязать ключ (отпечаток / Face ID на устройстве; WebAuthn). Без ключа — **нет доступа в кабинет**. Кнопки «позже» нет. У клиента (будущее) — ключ опционален.

   **Решение v1.0 пилота (2026-07-03, директор):** **утверждаю**
   | | |
   |---|---|
   | Pro | Ключ **обязателен**; без ключа кабинет **недоступен**; «позже» **нет** |
   | Client (будущее) | Ключ **опционален** |
   | Политика | Добавить про ключ / биометрию на устройстве — [T-073](../backlog/бэклог/T-073-legal-смс-пилот-обновление-документов.md) |

   **На юриста v2.0:** ☑ **подтверждено 2026-07-05** — п.1–3; формулировки Passkey — T-073.

## ИИ-помощник по продажам (E-014)

**Контекст продукта:** в Pro — ИИ-помощник для тренера (рассказ → анкета → стратегии → недельный план и дневные задачи → совещание). ИИ **не** пишет клиентам сам; черновики и задачи — для тренера. Шлюз — **Caila** (модели OpenAI и др.). Канон: [sales-стратегический-слой](../../_telotron.ru/docs/Техдок/03-модули/sales-стратегический-слой.md) (§4.1, §4.9, §4.10б) · [ADR-011 доп. 2](../../_telotron.ru/docs/Техдок/00-мета/архитектурные-решения/ADR-011-leadgen-утренний-бриф.md) · [ethics-and-law.md](../11-AI-инженер/Работа/e-014-kartochki/ethics-and-law.md).

**Статус оценки:** внутренний совет проекта (**2026-10-13**). **Не** заключение внешнего юриста. Спорные места — на подтверждение профильному юристу перед широким выкатом / обновлением legal v2.x.

**Шкала вердикта:** «допустимо как есть» · «допустимо с правками» · «недопустимо».

25. **Передача данных тренера во внешний ИИ-сервис (Caila / модели).** В модель: анкета тренера + обезличенные агрегаты воронки. Имена и контакты клиентов в стратегический контур **не** передаются. В брифе — макросы `{{name_N}}`. В политике / соглашении / согласиях ИИ и Caila **пока не** указаны.

   **Вердикт: допустимо с правками.**

   | # | Ответ |
   |---|--------|
   | 1 | **Да** — указать **Caila** (и при необходимости класс «провайдер ИИ / модели») как **лицо, привлекаемое к обработке** / обработчика по поручению в политике; цель — работа помощника по продажам. |
   | 2 | **Отдельное согласие на первый запуск помощника** — **да** (явный opt-in), плюс абзацы в политике и соглашении. Одного «тихого» пункта в политике **недостаточно**: есть внешний подрядчик и возможная **трансграничность**. Основание «исполнение договора» можно обсуждать с профильным юристом, но для пилота безопаснее **согласие + прозрачность**. |
   | 3 | **Трансграничная передача** — если запрос уходит к модели за рубежом: раскрыть в политике (страны / факт «в т.ч. вне РФ»), цель, меры; проверить необходимость **обновления уведомления РКН**; не опираться только на «данные обезличены» — анкета тренера (специализация, услуги, цель) — это **ПДн тренера**. |

   **Черновик UI (первый запуск помощника):**

   > «Помощник использует внешний сервис обработки текста (Caila и связанные модели ИИ). В обработку уходят сведения из вашей анкеты и обезличенные цифры работы (без имён и контактов клиентов). Данные могут обрабатываться за пределами РФ. Продолжая, вы соглашаетесь с этим. Подробнее — в [Политике конфиденциальности].»

   **В политику (кратко):** цель «ИИ-помощник Pro»; категории; Caila как привлечённое лицо; возможная трансграничность; срок / удаление рассказа (§26); что **не** передаём (контакты клиентов).

   **На профильного юриста:** основание обработки (согласие vs договор); формулировка трансграничности под фактическую схему Caila; РКН.

26. **Рассказ тренера: чужие ПДн (в т.ч. здоровье) внутри свободного текста.** Меры: очистка телефонов / почты / ссылок / известных имён до модели и до сохранения; сырой текст не храним; очищенный рассказ — **30 дней** после подтверждения анкеты, затем только `about`. Очистка неидеальна.

   **Вердикт: допустимо с правками.**

   | # | Ответ |
   |---|--------|
   | 1 | Меры — **хороший минимум**, но **недостаточны одни**: нужен **явный запрет/предупреждение в UI** до записи/отправки; риск «проскочившего» имени и особых категорий (здоровье третьих лиц) остаётся. |
   | 2 | Срок **30 дней** после подтверждения — **допустим** как временное хранение для споров/переразбора; предпочтительно **удалять очищенный рассказ сразу после подтверждения анкеты** (или ≤ 7 дней), оставляя только `about`. **30 дней — верхняя граница**, не цель. |
   | 3 | **Предупреждение в UI — обязательно** (не опционально). |

   **Черновик UI (экран рассказа):**

   > «Не называйте клиентов по имени и не пишите об их здоровье, диагнозах или личной жизни. Укажите только то, что относится к **вам** и вашей работе. Чужие персональные данные в рассказ лучше не включать.»

   **Дополнительно:** при срабатывании очистки — мягкий тост: «Убрали похожие на контакты фрагменты»; в политике — что тренер **не должен** вносить ПДн третьих лиц; при явном мед. содержании о третьих лицах — не использовать для обучения / few-shot.

   **На профильного юриста:** достаточно ли очистки + UI при остаточном риске; срок 7 vs 30 дней.

27. **Наблюдения о тренере (профилирование).** Закрытый список из 9 тем; тренер видит и может скрыть; анкету система **не** меняет сама; хранение 1 год; без подтверждения фактами 8 недель → неактуально; юридически значимых решений по наблюдениям нет.

   **Вердикт: допустимо с правками.**

   | # | Ответ |
   |---|--------|
   | 1 | **Отдельное согласие на «профилирование» не обязательно**, если: (а) это описано в политике как часть работы помощника; (б) нет автоматических юридически значимых последствий (блокировка, смена тарифа, отказ в услуге); (в) тренер может скрыть наблюдение. Достаточно **уведомления в политике + прозрачности в UI**. |
   | 2 | Прозрачность (видеть + скрыть) — **достаточна** при условии п.1. |
   | 3 | Ограничения формулировок: **гипотезы**, не приговор; без ярлыков личности («ленивый», «ненадёжный»); только поведение/паттерны из закрытого списка тем; без имён клиентов; ≤ 300 знаков — ок. |

   **Черновик в политике:**

   > «Помощник может формировать **наблюдения** о том, как вы работаете с планом и каналами (например, время ответов, выполнение выполнения задач). Это подсказки для вас, а не оценка личности. Вы видите все наблюдения и можете скрыть неверные. На их основе мы **не** принимаем решений об отказе в доступе к сервису.»

   **Запрет продукту:** не использовать наблюдения для автоматического штрафа, ограничения функций или передачи третьим лицам «скоринга тренера».

28. **Сообщения бывшим клиентам и знакомым: реклама (ст. 18 ФЗ «О рекламе») или нет.** Пишет **тренер** со своего аккаунта, по одному, без рассылок; стратегия — «как дела» + одно напоминание без ответа.

   **Вердикт: допустимо с правками** (для подсказок платформы; риск на стороне тренера как отправителя).

   | # | Ответ |
   |---|--------|
   | 1 | **Не любое** личное сообщение = реклама. Риск **рекламы** растёт, если есть предложение услуг / цены / «запишитесь» **и** канал связи (мессенджер, SMS, e-mail) **без** предварительного согласия адресата на рекламу. Чистое «как дела, давно не виделись» знакомому — обычно **ниже** риск рекламного состава, но грань тонкая. Массовая рассылка / база / незнакомые — **недопустимо** (уже в ethics). |
   | 2 | **Разрешено подсказывать:** личный контакт людям, которые **знают** тренера или **сами** проявили интерес; одно вежливое напоминание без давления. **Нельзя подсказывать:** холодные ЛС незнакомцам, купленные базы, массовые рассылки, игнор просьбы «не писать», обещания результата/медэффекта. |
   | 3 | **Подсказка тренеру в UI — нужна.** |

   **Черновик UI (задача «написать бывшему»):**

   > «Пишите **лично** и только тем, кто вас знает или сам обращался. Не рассылайте одно и то же многим сразу. Если человек просил не беспокоить — не пишите. Предложение услуг в мессенджерах может считаться рекламой — при сомнении спросите согласие или ограничьтесь коротким личным приветствием без оффера.»

   **Сверка с ethics (T-140, 2026-10-14):** в [ethics-and-law](../11-AI-инженер/Работа/e-014-kartochki/ethics-and-law.md) зафиксировано: **одно** напоминание без ответа на первое сообщение; **до двух** — только если с человеком уже был разговор. 29. **Карточка «Этика и закон»** ([ethics-and-law.md](../11-AI-инженер/Работа/e-014-kartochki/ethics-and-law.md)).

   **Вердикт: допустимо с правками.**

   | Тема | Оценка |
   |------|--------|
   | Кому писать / отказ / не базы | **Верно** — оставить |
   | Не обещать цифры / медэффект / ложную срочность | **Верно** — оставить |
   | Фото, отзывы, согласие | **Верно**; усилить: отзыв **с цитатой имени** — только при явном согласии на публикацию |
   | Контакты знакомых | Формулировка «не просить контакты — предложить переслать» — **верна**; добавить: не публиковать чужие ФИО/телефоны в постах без согласия |
   | Маркировка рекламы | Сейчас слабо («уточнить правила площадки») — **добавить**: при **платном** продвижении / рекламных постах — соблюдать требования о маркировке рекламы (ЕРИР и др. по актуальным правилам); платформа **не** гарантирует соответствие конкретной площадки |
   | Напоминания | Согласовать с §28: **≤ 1** повтор без ответа (или явно «не более двух» после решения директора) |
   | Лишнего не обещали | Не писать «помощник гарантирует законность ваших сообщений» — ответственность за отправку у тренера |

   **Чего не хватает (добавить в карточку):**
   1. Не публиковать в соцсетях **ПДн клиентов** (фото лица, ФИО, переписка) без согласия.
   2. Не использовать пересланные контакты знакомых как базу для холодных сообщений от тренера (только если знакомый сам написал).
   3. Не давать юридических/налоговых советов («оформите самозанятость так-то») — вне компетенции помощника.
   4. Явно: **платформа не отправляет** сообщения от имени тренера.

   **На профильного юриста:** вычитка итоговой редакции карточки перед prod E-014.
