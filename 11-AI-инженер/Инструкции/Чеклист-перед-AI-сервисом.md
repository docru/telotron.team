# Чеклист перед AI-сервисом

Использовать **до** merge в prod и при смене модели/промпта на stage→prod.

## 1. Продукт

- [ ] Задача и критерий успеха сформулированы (что пользователь получает).
- [ ] Понятно: **ядро** или **аддон** ([модель-монетизации](../../../_telotron.ru/docs/Бизнес-требования/00-канон-mvp/модель-монетизации-платформа.md), DEC-007).
- [ ] Есть fallback без ИИ или явный disable при сбое провайдера.

## 2. Модель и промпт

- [ ] Провайдер/модель зафиксированы; альтернатива на случай outage (хотя бы «выключить»).
- [ ] Промпт **версионирован** (id/дата); изменение = новая версия.
- [ ] Контракт ответа (JSON/поля) описан; парсер устойчив к мусору.
- [ ] Ограничения: max tokens, температура, таймаут.

## 3. Данные

- [ ] В промпт уходит **минимум** ПДн; нет лишних ФИО/телефонов/историй без нужды.
- [ ] Логи: без ключей API; без полного сырого ПДн (или маскирование).
- [ ] Retention логов/ответов согласован с юристом при сомнении.

## 4. Качество и стоимость

- [ ] Golden set (≥ N примеров) прогнан; известны fail-кейсы.
- [ ] Оценка **$ / запрос** и потолок на пользователя/сутки (если нужно).
- [ ] Нет бесконечных ретраев, раздувающих счёт.

## 5. Интеграция

- [ ] Вызов через сервис/job модуля, не «из UI напрямую к провайдеру».
- [ ] Идемпотентность / дедуп повторных кликов.
- [ ] Ошибки провайдера → понятный UX (согласовано с UI/UX).
- [ ] Feature-тест с **моком**; live-вызов — только stage/eval.

## 6. Выкладка

- [ ] Ключи в env; сисадмин в курсе.
- [ ] Runbook: провайдер лежит → что делаем.
- [ ] Наблюдаемость: success rate, latency, cost (хотя бы вручную на старте).

## После выкладки (7 дней)

- [ ] Срез fail/cost; при деградации — откат промпта или disable.
- [ ] Заметка в `11-AI-инженер/Работа/` (без секретов).
