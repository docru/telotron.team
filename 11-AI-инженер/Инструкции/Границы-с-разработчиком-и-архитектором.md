# Границы с разработчиком и архитектором

## Кто что решает

| Решение | Владелец | Согласование |
|---------|----------|--------------|
| Нужен ли AI в фиче | Директор / PO | LLM-инженер (feasibility, cost) |
| Провайдер и модель | LLM-инженер | Директор при бюджете; сисадмин при доступе |
| Текст промпта и схема ответа | LLM-инженер | PO при продуктовых формулировках |
| HTTP/job API модуля | Разработчик | Архитектор при новом контуре |
| Где живёт код (`Modules/…`) | Архитектор + разработчик | LLM-инженер — только AI-адаптер |
| Offline / PWA поведение без сети | Архитектор + разработчик | LLM: очередь или «нет ИИ офлайн» |
| Ключи и env | Сисадмин | LLM-инженер — список нужных секретов |
| Eval / golden set | LLM-инженер | Тестировщик — UI-сценарии вокруг |

## Типичный раздел труда на задаче

1. **LLM-инженер** — спецификация: вход, выход, промпт vN, критерии качества, лимиты, fallback.
2. **Разработчик** — эндпоинт/job, сохранение результата, UI, feature-тесты без живого платного вызова (моки).
3. **LLM-инженер** — прогон eval на stage с реальным провайдером; правка промпта.
4. **Тестировщик** — приёмка пользовательского сценария (кнопка → результат / ошибка).

## Не дублировать

- LLM-инженер **не** подменяет архитектора по зонам Pro/Client и канону API.
- Разработчик **не** меняет prod-промпт «на глаз» без версии и короткого eval (если LLM-роль назначена).
- Архитектор **не** выбирает модель вместо LLM-инженера, но **блокирует** обход модульных границ («прямые вызовы из Controllers в обход сервиса»).
