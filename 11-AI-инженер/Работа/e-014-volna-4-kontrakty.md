## 1) `data_quality` и когда задавать вопросы

### 1.1 Значения

| Значение | Смысл | Типичное поведение |
|----------|-------|--------------------|
| `sufficient` | Хватает для направления и плана | Диагноз без обязательных вопросов; на онбординге `questions` пустой |
| `partial` | Есть пробелы, но направление видно | Диагноз + `assumptions`; вопросы — только если критичны (онбординг) или полезны (совещание) |
| `insufficient` | Без ответа нельзя выбрать между принципиально разными путями | На онбординге: вопросы обязательны (если раунд не финальный). На финальном раунде — диагноз с явными `assumptions`, без вопросов |

Код **не** вычисляет `data_quality` сам — берёт из ответа Диагноста, но проверяет согласованность (§5).

### 1.2 Онбординг / ручной цикл (`mode = strategy_run`)

Спрашивать (до 3 за раунд), только если ответ **меняет выбор стратегии**, например:

- база `10_30`/`gt30`, но неясно: писали ли им за последние месяцы → `base_untouched` vs уже пробовали;
- каналы несколько, неясно какой основной для контента;
- предложение в анкете есть, в рассказе другое — что актуально.

**Не спрашивать** (идти в допущение), если:

- можно выбрать безопасный путь по умолчанию («есть база → сначала база»);
- поле уже в справочнике анкеты и заполнено;
- вопрос «ради интереса», не влияет на стратегию.

При `final_round = true` вопросы **запрещены** схемой: только диагноз + `assumptions`.

### 1.3 Недельное совещание (`mode = weekly`)

Вопросы шире: всё, что улучшит план следующей недели или уточнит наблюдение. Пересчёта диагноза по ответам нет — ответы в контекст следующей недели / следующего цикла.

Примеры: «что мешало выполнить план», «какой канал реально открывали», «готовы ли просить рекомендации».

### 1.4 Допущения (`assumptions`)

Каждое: коротко (≤160), без имён, с пометкой что это допущение. Тренер видит их в диагнозе. На совещании спорное допущение можно превратить в вопрос или в предложение правки анкеты (если подходит под §3).

## 2) Формат уточняющих вопросов

### 2.1 Поля одного вопроса

| Поле | Тип | Правило |
|------|-----|---------|
| `key` | string | стабильный ключ раунда, латиница/`snake_case`, уникален в массиве |
| `text` | string | ≤ 120, простой язык, один вопрос |
| `why` | string | ≤ 120, «зачем спрашиваем» — польза для тренера, не для системы |
| `options` | string[2..5] | короткие варианты, ≤ 60 каждый |
| `allow_free_text` | bool | см. §2.2 |
| `profile_field` | string\|null | поле `SalesGrowthProfile` или null |

### 2.2 Свой текст (`allow_free_text`)

| `profile_field` | `allow_free_text` |
|-----------------|-------------------|
| задан (поле со справочником: `services`, `channels`, `hours_per_week`, `urgency`, `offer`, `old_base_size`) | **false** — только варианты из справочника |
| null (смысловой вопрос) | **true** — варианты + «свой ответ» |

Код отвергает вопрос, если `profile_field` задан и `allow_free_text = true`, или варианты не из справочника поля.

**Какие поля можно спрашивать (`askable_fields`, после прогона v1.1).** Код передаёт Диагносту `askable_fields` — поля анкеты, которые пусты (`null` / `[]`) или есть в `mismatch_flags` — и `profile_allowed` только для них. Заполненное поле не переспрашиваем: gpt-4o-mini без этого в каждом втором кейсе спрашивала «Насколько срочно вам нужны клиенты?» у тренера, который уже ответил. Промптом не лечится — схема вопросов собирается кодом под запрос (`anyOf`: смысловой вопрос или вопрос по одному из `askable_fields` с `enum` кодов). Подробно — [отчёт прогона](e-014-strategic-eval-v1.md) §5.

### 2.3 Как писать «зачем»

- От первого лица пользы: «Чтобы не предлагать писать тем, кому вы уже писали».
- Без жаргона («для скоринга», «для RAG»).
- Без давления и упрёка.

### 2.4 Привязка к профилю

Ответ с `profile_field` **сразу** пишется в анкету (слова тренера). Остальные — в контекст Диагноста на 90 дней.

Поля, которые Диагност **может** уточнять через `profile_field`: `old_base_size`, `channels`, `hours_per_week`, `urgency`, `offer`, `services`.  
Не через вопрос (только карточка онбординга / форма): `specialization`, `goal_clients_per_month` — обязательные, код уже требует до подтверждения.

## 3) Темы наблюдений и правка анкеты

### 3.1 Закрытый список `topic`

| `topic` | Смысл | Откуда сигнал |
|---------|-------|---------------|
| `channel_performance` | Один канал даёт заявки / касания заметно лучше других | заявки и задачи по каналам |
| `time_pattern` | Тренер действует в другие дни/объём, чем заявлено | выполнение задач по дням недели |
| `load` | Факт нагрузки выше или ниже `hours_per_week` / интенсивности | минуты задач vs потолок |
| `offer` | Предложение или запись не работают / не используются | заявки со страницы, выполнение `offer_*` |
| `audience` | По факту другая аудитория, чем в рассказе/`about` | источники контактов, формулировки тренера |
| `base_usage` | База есть в CRM, но касаний мало (или наоборот) | `legacy_base` vs касания |
| `follow_up_gap` | Много «зависших» диалогов | `in_progress` + remind |
| `plan_fit` | Пункты плана систематически не выполняются или вычёркиваются | выполнение плана, `is_edited` |
| `skill_signal` | Повторяющийся пробел навыка (для будущего образовательного слоя) | отклонения, провалы однотипных задач |

Новый `topic` = новая версия схемы Диагноста.

### 3.2 Наблюдение vs предложение правки

| `kind` | Когда | Что видит тренер |
|--------|-------|------------------|
| `observation` | Заметка без смены анкеты | «Что заметил помощник», можно скрыть |
| `profile_change` | §3.3 | На совещании: «Поправить …?» → принять / отклонить |

Текст наблюдения: ≤ 300, без имён, без «клиентов: 0».

### 3.3 Когда `profile_change` (решение PO)

Предлагать правку поля анкеты **только если**:

1. Прошло **не меньше 2 полных недель** с подтверждения анкеты или последней правки этого поля; и
2. **Две недели подряд** факты расходятся с текущим значением (пример: `hours_per_week = gt5`, а выполнение ≤ потолка `light` обе недели); и
3. Есть одно предложенное значение из справочника; и
4. Поле из списка: `hours_per_week`, `urgency`, `channels`, `old_base_size`, `offer` (не `specialization` / цель в MVP).

Иначе — только `observation` без кнопки правки.

Код на входе Диагноста может передать флаги «поле X расходится N недель» — модель не считает календарь сама; если флагов нет, `profile_change_proposals` должен быть пустым (проверка кода).

## 4) Схемы ответов (обзор)

Файлы: [e-014-schemas/](e-014-schemas/). Обёртка как у брифа: `type: json_schema` + `strict: true`.

| Файл | Сценарий | Режим |
|------|----------|-------|
| `strategic.intake_extract.v1.schema.json` | разбор рассказа | один |
| `strategic.diagnose.v1.schema.json` | Диагност | `strategy_run` и `weekly`; при `final_round` — `questions` maxItems 0 (отдельный prompt / одна схема с max 3, код режет) |
| `strategic.propose.v1.schema.json` | Стратег | 2–3 варианта |
| `strategic.decompose.v1.schema.json` | Декомпозер | вехи + план недели |
| `strategic.review.v1.schema.json` | Монитор | статус + рекомендация |

### 4.1 Общие запреты (все тексты для тренера)

- Нет имён, телефонов, ников, адресов.
- Нет обещаний результата в цифрах и сроках.
- Нет медицинских обещаний.
- Нет строки про клиентов, если в контексте `clients_new = 0` / клиенты не переданы.
- Тон: сильные стороны → возможности, без упрёка.

Детальный список проверок кода — [e-014-volna-4-proverki.md](e-014-volna-4-proverki.md).

### 4.2 Диагност — поля `payload`

| Поле | Онбординг | Совещание |
|------|-----------|-----------|
| `data_quality` | да | да |
| `strengths` | 1–4 | 1–4 |
| `bottlenecks` | 1–4 кода из списка | 1–4 |
| `hypotheses` | 0–4 | 0–4 |
| `opportunities` | 1–3 | 1–3 |
| `skill_gaps` | 0–3 | 0–3 |
| `assumptions` | 0–5 | 0–5 |
| `questions` | 0–3; при `final_round` — 0 | 0–3 |
| `observations` | обычно 0 | 0–5 |
| `profile_change_proposals` | 0 | 0–2 по §3.3 |

`bottlenecks[].code` — из [типов §2](e-014-volna-4-tipy-i-kartochki.md#2-коды-узких-мест-bottlenecks); `text` — формулировка для тренера (возможность, не упрёк).

### 4.3 Стратег

Массив `strategies` длины 2..3. Ровно одна с `is_recommended: true`.  
`knowledge_card_keys` — подмножество ключей, переданных во входе (код сверяет).  
`name` ≤ 60, `summary` ≤ 300, без обещаний цифр.

### 4.4 Декомпозер

- `milestones` — только при первом плане после выбора стратегии; на недельном вызове может быть `[]` (вехи уже есть).
- `items` плана: 1–10 пунктов; типы из `strategy.*`; есть `hint` ≤ 200; частота `once` \| `daily` \| `{times_per_week: N}`.
- Суммарные минуты недели ≤ потолка интенсивности (100 / 180 / 360).

### 4.5 Монитор

- `status`: `on_track` \| `behind` \| `failed` \| `too_early`
- `recommendation`: `continue` \| `adjust` \| `change_strategy`
- `too_early` обычно без ИИ (код); если модель вернула — допустимо в первые 7 дней стратегии
- Не ставить `failed` только из‑за нуля клиентов

## 5) Согласованность `data_quality` и вопросов (проверки кода, черновик)

| Условие | Действие кода |
|---------|---------------|
| `final_round` и `questions` не пуст | отклонить ответ |
| `data_quality = insufficient` и не `final_round` и `questions` пуст (онбординг) | отклонить или запросить retry |
| `data_quality = sufficient` и `questions` не пуст (онбординг) | предупреждение / отрезать вопросы (предложение: отрезать) |
| вопрос с `profile_field` и `allow_free_text` | отклонить |
| `profile_change` без флага «2+ недель расхождения» на входе | отбросить предложения |
| `bottlenecks.code` не из списка | отклонить |
| стратегии не 2–3 или ≠1 recommended | отклонить |

Полный чеклист — [e-014-volna-4-proverki.md](e-014-volna-4-proverki.md).

## 7) Few-shot: формат, отбор, обновление

По техдоку (§4.14) в MVP таблицы `sales_prompt_examples` нет — 1–3 сжатых примера лежат в файле промпта. Ниже — формат на потом и правила, которые уже действуют для примеров в файлах.

### 7.1 Главный урок прогона v1.1

gpt-4o-mini **копирует примеры дословно**: пример вопроса «Писали ли вы бывшим клиентам?» попадал в 8 из 10 ответов Диагноста, включая совещания, где ответ уже виден из фактов. Поэтому:

1. Примеры — **сжатые описания** («strengths про базу и канал; один смысловой вопрос про давность сообщений»), а не готовый JSON с текстами. JSON-шаблон — только для формата, с заглушками `<поле>`.
2. Для Диагноста (вопросы) few-shot из реальных кейсов **не используем** — вопросы должны быть про конкретного тренера.
3. Для Стратега и Монитора few-shot полезен (тексты шаблонны: «Эта стратегия подходит, так как…») — но **2–3 разных** примера, не один.

### 7.2 Запись примера («профиль → стратегия → результат»)

| Часть | Поля | Откуда |
|-------|------|--------|
| Профиль | `old_base_size`, `channels`, `hours_per_week`, `urgency`, `offer`, `intensity`; `specialization` — обобщённо («силовые», «йога») | `SalesGrowthProfile` на момент выбора |
| Диагноз | коды `bottlenecks`, `data_quality` | ответ Диагноста |
| Стратегия | `name`, `summary`, `knowledge_card_keys`, `is_recommended` выбранной | `sales_strategies` |
| Результат | `outcome` (техдок §4.10б): выполнение планов, вехи, диалоги, заявки, клиенты; итог Монитора (`status`) | снимок при архивации |
| Служебное | `prompt_version`, `model`, `source` (`ai` / `rules`), дата | |

Без имён, контактов, `about` и рассказа — только коды и числа. `specialization` — обобщённо, чтобы не узнать тренера.

### 7.3 Отбор в пример

Пример попадает в кандидаты, только если:

1. Стратегия прожила **≥ 4 недели** (иначе результат не показателен).
2. Выполнение планов **≥ 60%** — стратегию реально делали (иначе неизвестно, работает ли она).
3. Итог Монитора на последнем совещании — `on_track` или `behind` с ростом диалогов / заявок; `failed` — не в позитивные примеры, а в «чего избегать» (−2 в `KnowledgeScorer` уже есть).
4. Источник `ai` или `rules` — оба допустимы; помечаем, чтобы сравнивать.
5. Клиенты — **не критерий отбора** (решение PO), но сохраняются в записи для обучения и анализа.

### 7.4 Подстановка в промпт

- Для Стратега: 2 примера с тем же `old_base_size` и пересечением кодов узких мест с текущим диагнозом; разные карточки методик.
- Для Монитора: 1 пример `on_track` и 1 `behind` — чтобы модель видела оба исхода.
- **Никогда** — пример того же тренера (подгонка под себя).
- В промпте пометка: «Примеры — чужие тренеры, для формата и логики выбора; не копируй тексты».

### 7.5 Обновление

- Пересбор кандидатов — раз в месяц или при +20 архивных стратегий.
- Смена набора примеров = новая `prompt_version` + прогон набора `e-014-eval` (≥ 95%, Диагност / Стратег / Декомпозер / Монитор — 100%) до выкладки.
- Пример выбывает, если его карточка методики деактивирована или изменён закрытый список кодов.
