## 1) Типы задач стратегии `strategy.*`

Фиксированный список (техдок §8.2). Задачи **без привязки к контакту** (§8.3): «напишите пятерым из старой базы», не «напишите Марине». Код отбрасывает пункт плана с типом не из списка.

| Тип | Что делает тренер | Кнопка (`TaskAction`) | Мин. по умолч. | «Зачем» для брифа по правилам (≤160, без имён) |
|-----|-------------------|----------------------|----------------|-----------------------------------------------|
| `strategy.base_collect` | Внести в CRM бывших клиентов / знакомых | `crm` | 15 | Люди, которые вас уже знают, охотнее всего откликаются. Сначала соберём их в одном месте. |
| `strategy.base_reactivate` | Написать N людям из старой базы / знакомым | `crm` | 15 | Бывшие клиенты и знакомые уже вам доверяют — личное сообщение им чаще всего даёт первые ответы. |
| `strategy.follow_up` | Напомнить о себе тем, кто не ответил или «подумает» | `crm` | 10 | Многие отвечают только на второе сообщение — короткое напоминание возвращает разговор. |
| `strategy.trial_convert` | Предложить следующий шаг: встречу/пробную откликнувшимся **или** продолжение после пробной | `crm` | 10 | После пробной интерес самый высокий — самое время предложить продолжение. Тем, кто откликнулся в переписке, — предложить встречу или пробную. |
| `strategy.referral_ask` | Попросить довольных клиентов порекомендовать вас | `crm` | 10 | Рекомендация от клиента — самое тёплое знакомство: новому человеку уже есть причина вам доверять. |
| `strategy.offer_setup` | Сформулировать предложение и проверить страницу записи | `lead_page` | 20 | Понятное предложение и простая запись помогают записаться без долгой переписки. |
| `strategy.link_share` | Поставить ссылку на запись в профиль, сообщения, посты | `lead_page` | 10 | Ссылка на запись там, где вас видят, позволяет записаться без лишних вопросов. |
| `strategy.social_profile` | Оформить профиль в соцсети: кто вы, для кого, как записаться | — | 20 | По профилю решают, писать ли вам. Понятная шапка и ссылка на запись снимают лишние вопросы. |
| `strategy.listing_setup` | Оформить / обновить анкету на площадке услуг (Авито Услуги, Профи.ру и т. п.) | — | 25 | На площадках услуг вас ищут люди с готовым запросом — понятная анкета и быстрый ответ помогают им написать. |
| `strategy.content_post` | Опубликовать пост | — | 30 | Регулярные посты напоминают о вас и показывают, как вы работаете. |
| `strategy.content_short` | Короткий формат: история, короткое видео, кружок | — | 10 | Короткие истории держат вас на виду у знакомых без больших затрат времени. |
| `strategy.community_engage` | Полезные ответы в тематических или местных чатах и сообществах | — | 15 | Полезный ответ в тематическом или местном чате знакомит с вами людей, которым это уже интересно. |
| `strategy.partner_outreach` | Договориться с партнёром: клуб, массажист, нутрициолог, магазин, автор канала | — | 30 | Партнёр рекомендует вас людям, которые ему доверяют, — без рекламы. |
| `strategy.review_collect` | Попросить отзыв или результат клиента (с согласия) | — | 10 | Отзывы и результаты клиентов отвечают на главный вопрос новых людей: «а мне поможет?» |

**`trial_convert` — два контекста, один тип.** (1) В `follow-up-routine` — продолжение **после** пробной / консультации. (2) В `reactivate-old-base` — предложить встречу или пробную тем, кто **уже откликнулся** в переписке. Различие — в `title` / `hint`. Отдельный тип в MVP не заводим. Пока в CRM нет отметки пробной — в вехах критерий `trial_convert` не ставить; в hint — «если таких людей нет — задача выполнена».

**Порядок внутри уровня «план недели»** в `CandidatePreparer` (бриф v2): `base_reactivate` → `follow_up` → `trial_convert` → `referral_ask` → `base_collect` → `offer_setup` → `link_share` → `partner_outreach` → `listing_setup` → `community_engage` → `content_post` → `content_short` → `social_profile` → `review_collect`. Сначала — действия с людьми (ближе к записи), затем подготовка, затем контент.

**Старые типы `plan.*`.** В E-014 плана из анкеты нет — `plan.*` перестают создаваться. Остаются в enum на время перехода (старые задачи пилота), в контракт брифа v2 не входят.

**Бриф v2.** Новые типы меняют контракт промпта брифа (`TaskType`: «новый тип → новая версия промпта») → `morning_brief.v2` + обновление набора T-138 (волна 5).

## 2) Коды узких мест (`bottlenecks`)

Нужны в ответе Диагноста **кодом**, чтобы `KnowledgeScorer` сопоставлял их с карточками. Текст для тренера — отдельным полем.

| Код | Смысл | Чем может подтвердить код |
|-----|-------|---------------------------|
| `base_untouched` | Есть старая база / знакомые, но им не пишут | `old_base_size` = `10_30`/`gt30`, мало контактов `legacy_base` или касаний; вместе с `no_base` — нельзя |
| `no_base` | Базы нет, начинать с нуля | `old_base_size` = `none`/`lt10` |
| `low_visibility` | О тренере мало кто знает: нет контента / профиля | нет выполненных `content_*`, `social_profile` |
| `weak_offer` | Нет понятного предложения или удобной записи | нет заявок со страницы записи, `offer_note` пуст |
| `slow_response` | Долго отвечает на заявки | возраст `crm.reply_new_contact` |
| `no_follow_up` | Диалоги затухают без напоминаний | много `crm.remind_stale`, контакты висят в `in_progress` |
| `low_conversion` | Диалоги есть, клиентов мало | `in_progress` есть, переходов в `client` нет |
| `no_referrals` | Не использует рекомендации действующих клиентов | есть `client`, нет `referral_ask` |
| `irregular_activity` | Действует рывками | выполнение задач неравномерно по неделям |

Список закрытый; новый код = новая версия схемы Диагноста.

## 3) Метрики критериев вех

Решение PO (блок А): критерии — **действия тренера + промежуточные результаты**. Новые клиенты — только факт на совещании, не критерий.

| Метрика | Что считает код | Вид |
|---------|-----------------|-----|
| `tasks_done` | выполненные задачи стратегии, опционально `task_type` | действие |
| `contacts_added` | новые контакты CRM, опционально `source` (`legacy_base`, `manual`, `referral`, …) | действие |
| `dialogs_started` | контакты, перешедшие в `in_progress` | промежуточный результат |
| `leads_new` | новые заявки / обращения: страница записи, квиз, обратный звонок **и** ручной ввод обращения из личных сообщений (`dm` / аналог) | промежуточный результат |

**`leads_new` и личка (T-140).** У тренеров много обращений приходит в ВК/ТГ, а не через страницу. Если считать только `booking_page` / `quiz` / `callback`, вехи «Появились заявки» занижены. **Предложение:** в MVP включать в `leads_new` контакты, которые тренер вручную отметил как обращение (источник вроде `dm`); в брифе подсказывать вносить такие обращения в CRM. Нужна правка техдока / CRM (архитектор). До реализации кода — в карточках заголовки вех уже нейтральные («Появились заявки»), без «со страницы».
| `trials` | пробные / консультации | **не в MVP** (решение директора 2026-10-13): в CRM нет отметки пробной; критерии вех без `trials`. Отметка в CRM — отдельная задача; после неё метрика включается |

### 3.1 Клиенты — факт и данные для обучения, не критерий

Уточнение PO (2026-10-10):

| Где | Что | Кто считает |
|-----|-----|-------------|
| Итоги недели (совещание) | `clients_new` — контакты, перешедшие в `client` за неделю и с начала стратегии; разбивка по `source` контакта | код, в `sales_meetings.facts` |
| Итог стратегии (архив) | снимок исхода: клиенты, заявки, разговоры за период стратегии + по `source`; выполнение планов; статус вех | код, при `archived` |
| Обучение и анализ ИИ | связка «профиль → диагноз → стратегия / карточки → выполнение → промежуточные результаты → клиенты» | код (агрегаты), AI-инженер (анализ) |

Зачем это для ИИ:

- **`KnowledgeScorer`** — бонус «историческая успешность» карточки ([Скоринг §5.1](Агенты/Скоринг.md)) считается по клиентам и разговорам у похожих тренеров.
- **Few-shot** — примеры «профиль → стратегия → результат» для Стратега отбираются по исходу.
- **Оценка моделей и промптов** — сравнение версий не только по валидности ответа, но и по исходу стратегий (набор на реальных данных пилота, решение PO блок А п. 4).
- **Эффект подключения агентов** — сравнение «до / после» и «с ИИ / по правилам» (`source` стратегии и плана): растут ли разговоры, заявки и клиенты.

Ограничения:

- Клиенты **не влияют** на статус вех; `Monitor` видит их как контекст, но вывод `failed` по одним клиентам не делает.
- **Нет новых клиентов — строку о клиентах тренеру не показываем вовсе** (никаких «Клиентов: 0»). Есть — показываем. Правило для экрана итогов, совещания, брифа и всех текстов агентов; в данных для обучения ноль пишется как есть.
- Тренеру не говорим «стратегия не сработала — клиентов нет». Подача по тону блока Б п. 3: сначала что сделано и что сдвинулось.
- В данные для обучения — только числа и коды, без имён и контактов. Связь «стратегия → клиент» приблизительная: клиент мог прийти не из-за стратегии; выводы — по многим тренерам, не по одному.

Формат критерия: `{ "metric": "dialogs_started", "min": 3, "since": "strategy_start" }` (+ `task_type` / `source` при необходимости). Код сам считает выполнение — модель не решает, достигнута ли веха.

## 4) Формат карточки методики

Файл `resources/sales/knowledge/<key>.md`: YAML-заголовок (метаданные для кода) + тело (текст для модели).

```yaml
---
key: reactivate-old-base          # стабильный, латиница через дефис
kind: algorithm                   # algorithm | tactic | template | restriction
version: 1
title: Вернуть бывших клиентов    # ≤ 60
summary_for_trainer: >-           # ≤ 300, простыми словами, без обещаний результата
  ...
fit:                              # жёсткий фильтр: значение профиля должно входить в список; нет ключа — подходит всем
  old_base_size: ["10_30", gt30]   # значения с «_» — в кавычках, иначе YAML читает число
bottlenecks: [base_untouched]     # мягкое совпадение с диагнозом — для KnowledgeScorer
default_tasks:                    # обязателен для algorithm и tactic
  light:
    - type: strategy.base_reactivate
      title: Напишите 2 людям из старой базы   # ≤ 100, без имён
      frequency: { times_per_week: 1 }         # once | daily | { times_per_week: N }
      minutes: 15
      when: every_week                          # first_week | every_week
      hint: Начните с тех, с кем расстались хорошо. ...   # ≤ 200, подсказка-обучение
  moderate: [...]
  intense: [...]
default_milestones:               # горизонт 6 недель
  - position: 1
    title: База собрана и первые сообщения отправлены
    week: 2
    criteria:
      - { metric: contacts_added, source: legacy_base, min: { light: 5, moderate: 10, intense: 15 } }
---
Тело для модели: когда применять, шаги, на что смотреть, ограничения.
```

Правила для кода (`sales:knowledge-sync`):

- `key` уникален и совпадает с именем файла; `kind` из списка.
- `fit` — только поля профиля и значения из справочников (`SalesGrowthProfile`).
- `bottlenecks` — только коды из §2.
- `default_tasks` обязателен для `algorithm` / `tactic`, есть все три интенсивности; типы — из §1; `minutes` 5–60; `hint` ≤ 200.
- Нагрузка набора на неделю (минуты × частота) не выше: `light` ≤ 100, `moderate` ≤ **180**, `intense` ≤ 360 (`sales.strategic.weekly_minutes`, решение директора 2026-10-13) — **проверка по одной карточке**.
- Сумма минут **алгоритм + тактики** одной стратегии тоже ≤ потолка недели — у Декомпозера / `TemplateWeekPlanner` (сейчас `check_cards.py` это не ловит; follow-up для архитектора, T-140).
- `default_milestones` — метрики из §3, `week` 1–6, `min` по всем трём интенсивностям; для порогов на 2–4 неделе ориентир **~70%** полного плана, не 100% (ревью 2026-10-13).
- В `title` задач с числом людей писать **итог на неделю** («Напишите 5 людям за неделю»), чтобы не путать с `times_per_week`.

**Неделя 1 и дальше.** Первый план = пункты `first_week` + `every_week`; следующие недели = `every_week` (с поправкой Монитора — у Декомпозера; в наборе по правилам — как есть).

**Подсказка `hint`** — решение PO (блок Б, п. 4): обучение — короткой подсказкой внутри задачи, без отдельных пунктов плана. Декомпозер тоже пишет `hint` в пункты плана.

### 4.1 Поиск и ранжирование (предложение для `KnowledgeScorer`)

1. Фильтр: только активные карточки, все ключи `fit` совпадают с профилем.
2. Счёт: +3 за каждый общий код `bottlenecks` с диагнозом (при стратегиях по правилам диагноза нет → 0), +1 если `kind = algorithm` (целостнее для стратегии), −2 если карточка была в прошлой стратегии с итогом `failed`.
3. Топ-5 Стратегу (`restriction` — всегда целиком, вне топа); топ-3 `algorithm`/`tactic` — стратегии по правилам.
