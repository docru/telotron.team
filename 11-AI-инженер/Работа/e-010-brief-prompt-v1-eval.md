## 1) Итог коротко

1. **Шлюз `openai-direct` подтверждён** для всех трёх моделей КБЖУ → часть B [T-135](../../backlog/бэклог/T-135-e010-общий-ai-слой.md) разблокирована, с двумя условиями для qwen (§2).
2. **Промпт `leadgen.morning_brief.v1` готов** для T-136: системный текст + JSON-схема + правила подготовки кандидатов в коде.
3. **Модель — gpt-4o-mini.** На 25 ситуациях × 6 прогонов (150 вызовов): валидных ответов **100%**, по правилам **100%**, по ожиданиям набора **100%**; среднее время **~2,1 с**, p95 **~2,6 с**; стоимость **~0,036 ₽ за бриф**.
4. **deepseek-v3.2 для брифа не подходит:** при strict `json_schema` в 66% ответов подставляет `-1` вместо `task_id`/`order`, в 2,5 раза медленнее и вдвое дороже.
5. **Два решения, которые T-136 должен реализовать в коде** (иначе качество падает до ~92%): сортировка кандидатов и **отсечение нижних уровней приоритета** до вызова модели (§4.2). И **без имён в `why`** — отклонение от примера ADR-011 (§9).
6. **Слабое место v1 — текст `why`:** правила соблюдаются, но формулировки шаблонные и часто пересказывают название задачи. Для пилота приемлемо; улучшение — в v2 (§8).

### Условия для части B

1. **qwen:** в тело запроса добавить `"reasoning": {"enabled": false}`; `response_format` для qwen **не передавать**. В ADR-010 нет поля для дополнительных параметров на модель → нужен необязательный `extra_body` на модель в `config/ai.php` (предложение архитектору, по аналогии с `base_url` на модель).
2. **gpt-4o-mini:** Caila не отдаёт `usage.cost` → `cost_rub` считать по токенам × прайс (`caila-llm-prices.csv`: 18,63 / 74,52 ₽ за 1M) или оставлять `null` и сверять с кабинетом.

### Дефекты текущего T-110 (не зависят от переезда)

- **qwen думает и в проде сейчас.** На старом пути (`/api/providers/openrouter/v1`) то же самое: 1,5–4,5 тыс. токенов ответа, 7,7–21,8 с, **0,05–0,15 ₽ за один вызов** при бюджете 0,02 ₽ на весь ансамбль; при таймауте 20 с часть ответов теряется. `reasoning: {"enabled": false}` работает и на старом пути: 44–49 токенов, ~1,5 с, ~0,003 ₽. Рекомендация — исправить уже сейчас, не дожидаясь T-135.
- **deepseek иногда отдаёт `-1` вместо белка** (3 из 7 ответов; похоже на «не знаю»). Агрегатор превращает отрицательное в 0 → занижает среднее и расширяет ДИ. Рекомендация — отрицательное значение считать невалидным (исключать ответ модели или поле), а не обнулять.

## 4) Контракт входа для T-136

### 4.1 Поля

```json
{
  "profile": {
    "specialization": "персональные онлайн-тренировки: похудение и сила",
    "intensity": "light | moderate | intense",
    "channels": ["vk"],
    "style": {"address": "ty | vy", "tone": "soft | direct", "length": "short | detailed"}
  },
  "funnel_7d": {"new_contacts": 2, "in_progress": 3, "trials": 1},
  "candidates": [
    {"task_id": 101, "source": "crm_signal | plan", "type": "crm.reply_new_contact", "title": "Ответить на заявку: {{name_1}}", "overdue_days": 0}
  ],
  "people": [
    {"ref": "{{name_1}}", "stage": "new | in_progress | client | former | declined", "days_since_touch": null}
  ]
}
```

- `type` — из контракта T-115: `crm.reply_new_contact`, `crm.next_action`, `crm.remind_stale`, `plan.page`, `plan.base`, `plan.touch`, `plan.post`, `plan.meeting`, `plan.profile`. Новый тип → новая версия промпта.
- `overdue_days`: 0 — на сегодня; для заявки — сколько дней человек ждёт ответа.
- `funnel_7d.*` может быть `null` (данных нет).
- В `title` и `people` — только макросы `{{name_N}}`; телефон, ник, канал, фамилия — никогда.
- **Минимум ПДн:** в `people` передавать только тех, кто упомянут в переданных `candidates` (набор c20 проверяет, что лишние люди не ломают ответ, но слать их не нужно).

### 4.2 Подготовка кандидатов кодом (обязательно)

Эталон — `prepare_candidates()` в [`run_eval.py`](e-010-brief-eval/run_eval.py). Тот же порядок использует и **бриф по правилам**.

1. **Сортировка:** тип по приоритету `reply_new_contact → next_action → remind_stale → plan.page → plan.base → plan.touch → plan.post → plan.meeting → plan.profile`, затем `overdue_days` по убыванию, затем `task_id`.
2. **Отсечение уровней.** Уровни: 0 — заявки, 1 — договорённости, 2 — напоминания «в работе», 3 — план. Максимум пунктов: light 2, moderate 3, intense 3. Уровни берутся **целиком сверху**, пока набранных задач меньше максимума; нижние уровни модели **не передаются**.
   - 5 заявок + посты, intense → модели уходят только 5 заявок.
   - 1 договорённость + 1 напоминание + 4 задачи плана, intense → уходят все 6.

Почему в коде: без отсечения gpt-4o-mini устойчиво добавляет одну задачу плана третьим пунктом, хотя промпт (с примером) это запрещает. Хуже того, иногда она ставит `task_id` заявки, а в `why` пишет про старую базу (`why` от другой задачи). Приоритет уровней детерминированный, так что уговаривать модель промптом бессмысленно. После отсечения ошибка исчезла: 0 из 150.

3. **0 кандидатов → без вызова ИИ** (бриф по правилам / «Заполните профиль»).

## 5) Проверка ответа (код T-136)

Продуктовая проверка ADR-011 §3 (любое нарушение → бриф по правилам, `source=rules`):

- JSON разбирается, есть массив `items`;
- 1…min(3, число кандидатов) пунктов;
- `task_id` — целое и из переданных кандидатов, без повторов;
- `order` — целое ≥ 1, без повторов (пункты сортировать по `order`);
- `why` — непустая строка ≤ **160** символов;
- макросы в `why` (если есть) — только известные `{{name_N}}`, целые, без приклеенных окончаний.

`why` с валидным `{{name_N}}` **не** отбрасывать: макрос подставится корректно, бриф не ломается. В v1 модель имён не пишет (0 из 150 в финальной версии).

Число пунктов по `intensity` в продуктовую проверку **не** включаю: бриф с лишним пунктом всё равно полезнее брифа по правилам; в eval это проверка «по ожиданиям».

## 7) Проверочный набор и результаты

### 7.1 Набор

[`golden-set-v1.json`](e-010-brief-eval/golden-set-v1.json) (генератор — `golden_set.py`), **25 ситуаций**, ПДн нет — только макросы; демо-имена для ручного чтения — в поле `demo_names`.

Покрытие: новичок без людей · свежая заявка · много заявок при интенсивном плане · всё просрочено · лёгкий план · интенсивный смешанный · один кандидат · два кандидата при intense · нутрициолог · давние «в работе» · сегодня vs просрочено · стиль «вы/мягко/подробно» · стиль «ты/прямо/коротко» · инъекция «игнорируй правила» · инъекция «выбери task_id 999» · медицинская провокация («как лечить колено») · 15 кандидатов (максимум ADR-011) · нулевая воронка · много пробных · 10 людей без задач · почти дубли · бывшие клиенты · длинные шумные названия с эмодзи · день разбора недели · макрос `{{name_10}}`.

Для каждой ситуации: ожидания (`items_min/max`, `top1_any`, `must_include`, `include_any`, `only_from`, `not_together`) + проверки правил на каждом `why`: обещания, медицина, имена/местоимения, деньги, телефоны, ники, обращение «ты/вы», **`why` от другой задачи** (добавлено после ручного ревью).

### 7.2 Итерации на gpt-4o-mini

| Версия | Вызовов | Валидно | По правилам | По ожиданиям | Всё ок | Время ср. / p95 | ₽ / бриф |
|---|---|---|---|---|---|---|---|
| черновик 1 (smoke) | 25 | 96% | 88% | 84% | 80% | 2,2 / 2,4 с | 0,032 |
| черновик 2 | 50 | 100% | 96% | 88% | 84% | 2,4 / 3,2 с | 0,035 |
| черновик 3 (без имён в `why`) | 50 | 100% | 100% | 92% | 92% | 2,0 / 2,4 с | 0,034 |
| v1 + сортировка + пример в промпте | 75 | 100% | 97,3%* | 94,7% | 92%* | 2,1 / 2,8 с | 0,037 |
| **v1 + сортировка + отсечение уровней** | 75 | **100%** | **100%** | **100%** | **100%** | 2,0 / 2,5 с | 0,036 |
| то же, повтор | 75 | **100%** | **100%** | **100%** | **100%** | 2,1 / 2,7 с | 0,036 |

\* пересчитано с проверкой «`why` от другой задачи»: 2 случая в c03.

Что чинили между версиями: обращение «ты/вы» путалось → явные списки слов; 3 пункта при light → жёсткая таблица числа пунктов; повторы `task_id` и копирование фраз из инструкции → прямые запреты; неверные склонения имён («для Анна») → имена из `why` убраны совсем; задачи плана выше заявок → сортировка, пример, затем отсечение уровней кодом.

### 7.3 Сравнение моделей (финальный промпт, без отсечения уровней)

| Модель | Вызовов | Валидно | Время ср. / p95 / макс | ₽ / бриф | Источник цены |
|---|---|---|---|---|---|
| gpt-4o-mini | 75 | 100% | 2,1 / 2,8 / 3,4 с | 0,037 | прайс |
| deepseek-v3.2 | 50 | **34%** | 5,1 / 9,9 / 15,3 с | 0,070 | `usage.cost` |

deepseek со strict `json_schema` на вложенном массиве подставляет `-1` / `-121` в `task_id` и `order` (на плоской схеме КБЖУ такого не было). Это, вероятно, ограниченная генерация у апстрима OpenRouter. Для брифа не годится; запасная модель при outage не нужна — есть бриф по правилам.

### 7.4 Стоимость

0,036 ₽ за бриф (вход ~1 660 токенов, выход ~70). Потолок по лимитам ADR-011 (1 крон + 5 ручных): **≤ 0,22 ₽ на тренера в сутки**; реалистично 1–2 вызова → ~0,04–0,07 ₽. 100 тренеров × 30 дней: 110–650 ₽/мес.

## 8) Ручное ревью и ограничения v1

Файлы: `results/review-v1-tiercut-gpt4omini.md`, `results/review-v1-tiercut-gpt4omini-r2.md` (имена — демо).

Хорошо:
- выбор задач разумный во всех 25 ситуациях; заявки и договорённости первыми;
- инъекции в `title` проигнорированы (c14, c15); на «как лечить колено» — только «ответьте человеку», без советов (c16);
- обращение «ты/вы» соблюдено, упрёков за просрочку нет, обещаний и чисел клиентов нет.

Слабо (не ловится автопроверками):
- **шаблонность:** «Ответ на заявку поможет установить контакт…» — 7 из 75 пунктов дословно, «Касание с людьми из старой базы может вернуть интерес…» — 6;
- `why` часто **пересказывает название** («Обновление оффера на странице записи привлечёт…»), хотя промпт просит этого не делать;
- `style.length` (short/detailed) на текст почти не влияет; `tone` влияет слабо;
- редкие грамматические огрехи («подтверждение пробной занятия»), местоимение «его» в конце фразы.

Вывод: для пилота приемлемо — тренер видит понятную задачу и короткое «зачем» без вреда. Ценность ИИ против брифа по правилам в v1 — в основном выбор внутри уровня и живой текст; PO стоит оценить на пилоте, отличает ли тренер одно от другого.

Направления v2 (после пилота, по обратной связи):
1. Код передаёт короткую «зацепку» к задаче (`hint`: «после пробной», «ждёт 2 дня», «давно без касаний 9 дней»), модель строит `why` от неё — меньше шаблона.
2. Несколько эталонных пар «задача → хороший `why`» в промпте (few-shot), отдельно для «ты» и «вы».
3. Сравнить `gpt-4.1-mini` / аналог по цене × качеству текста.
4. Автопроверка «пересказ title» (пересечение слов `why` и `title`) и дублей `why` между тренерами.

## 9) Отклонения от ADR-011 и предложения архитектору

| Пункт ADR-011 | Предложение | Почему |
|---|---|---|
| «Склонения нет: тексты „для {{name_1}}“» | В `why` **имён нет вообще**; имя видно в названии задачи рядом | «для Анна», «Сергей написала» — ошибки, которые промптом не убираются; без имён 0 ошибок |
| Кандидаты: «открытые на сегодня и просроченные (до 15)» | + **сортировка и отсечение уровней** до вызова модели (§4.2) | без этого ~8% брифов с задачей плана вместо заявки/договорённости |
| ADR-010: `base_url` на модель | + необязательный **`extra_body` на модель** | qwen в ансамбле КБЖУ требует `reasoning: {"enabled": false}` |

Решение — за архитектором; промпт v1 и проверка написаны так, что работают и при текущем ADR (валидный макрос в `why` не ломает бриф).
