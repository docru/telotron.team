## 1) Продуктовые рамки (согласовано)

| Тема | Решение |
|------|---------|
| Кому отвечает ИИ в v1 | **Только тренеру**. Диалог с лидом — отдельный этап после каналов |
| Центр UX | Гибрид: **сценарии** (утро, совещание, онбординг) + **свободный чат** |
| Первый рабочий кусок | Сценарий **«утренний бриф»**: 1–3 задачи на день + «зачем» |
| Границы темы | Только продвижение/продажи услуг; отказ на медицину/питание клиента/юр.; без обещаний «N клиентов» |
| Тон | Из профиля тренера (кратко/подробно, мягко/прямо, «ты»/«вы») |

## 2) Главный принцип

**Состояние консультанта — в БД. LLM — слой рассуждения и языка поверх состояния.**

Модель не «помнит» сама. Код хранит профиль, план, навыки, метрики, выжимки; в запрос уходит только нужный кусок.

Код считает цифры и проверяет правила. Модель объясняет, предлагает, пишет тексты.

---

## 3) Модель состояния (что хранить)

Имена таблиц/полей — рабочие; финальные имена — с разработчиком/архитектором (часть уже в T-115).

| Сущность | Зачем |
|----------|--------|
| **GrowthProfile** | Специализация, ЦА, опыт, каналы, интенсивность, стиль, оффер |
| **Strategy** | Текущая стратегия + версия + причина смены |
| **Goal / Task** | Цели месяц/неделя/день; задачи со статусом и «зачем» |
| **SkillMap** | 8–12 навыков, уровень 0–3, уверенность, доказательства |
| **LessonLibrary** | Карточки микроуроков (пишет человек); ИИ выбирает и адаптирует |
| **ConversationSummary** | Выжимки прошлых диалогов (не вся история в каждый вызов) |
| **FunnelSnapshot** | Срез метрик из CRM (считает код) |
| **AiRun / AiTrace** | Трассировка: сценарий, шаги, tools, токены, latency, cost |

CRM-контакты, заметки, статусы — **E-006** (не дублировать). ИИ читает/пишет через доменный API с `author_type=ai`.

## 4) Контуры

### 4.1 Жизненный цикл (фазы, не один промпт)

1. Сбор профиля / сильные-слабые стороны / опыт продаж  
2. Стратегия продвижения  
3. Цели на месяц → неделю → день  
4. Ежедневный разбор воронки + приоритеты задач  
5. Микрообучение по ходу задач  
6. Итоги периода (совещание)

Каждая фаза **читает и пишет** состояние из §3.

### 4.2 Инициация

| Источник | Поведение v1 |
|----------|----------------|
| Событие CRM / подключение модуля | Ставит job сценария (онбординг, реакция на важное) |
| Крон | **Готовит** бриф заранее; не спамит пушами |
| Запрос тренера / открытие раздела | Показывает готовый бриф или запускает чат |

Лимит проактивных инициатив и тихие часы — заложить в конфиг; на пилоте упор на «готово к открытию раздела».

### 4.3 Обработка одного запуска

```text
триггер (событие / крон / сообщение)
        ↓
очередь (Laravel job)
        ↓
сценарий: morning_brief | onboarding | weekly_meeting | chat | generate_text | …
        ↓
сборка контекста из БД + макросы ПДн (§6)
        ↓
LLM (модель из конфига сценария)
  · фиксированный сценарий: 1 вызов → JSON
  · чат: tool calling, лимит шагов (напр. ≤5)
        ↓
валидация ответа / аргументов tools
        ↓
исполнение через доменные сервисы (не «сырой HTTP»)
        ↓
подстановка макросов → чат и/или запись в БД + аудит
```

## 5) Действия (tools) и безопасность

### Политика записи

| Тип | Поведение |
|-----|-----------|
| Чтение (снимок воронки, список контактов без ПДн-секретов, задачи) | Автоматически |
| «Безопасная» запись (задачи, заметки ИИ, обновление плана) | Автоматически + аудит |
| Смена статуса CRM | **Только после подтверждения тренера** |

`trainer_id` — **только из сессии/job-контекста**, никогда из ответа модели.

### Как вызывать действия

- **Чат:** нативный **tool calling** (проверить поддержку через Caila для выбранных моделей).  
- **Фиксированные сценарии (бриф, совещание):** модель возвращает JSON по схеме; код сам вызывает сервисы — без свободного агента.  
- **Не делать:** парсинг «команд» из свободного текста.

### Инструменты (черновой белый список)

Крупные операции, не мелкие CRUD:

| Tool | Назначение |
|------|------------|
| `get_daily_snapshot` | Профиль (кратко) + задачи сегодня + срез воронки |
| `list_contacts_for_touch` | Кандидаты на касание (без телефона в LLM) |
| `propose_tasks` / `upsert_tasks` | Предложить / записать задачи |
| `add_ai_note` | Заметка в CRM от ИИ |
| `propose_status_change` | Предложить смену этапа (нужно подтверждение UI) |
| `get_lesson` | Взять карточку микроурока по навыку |
| `update_skill_signals` | Записать сигналы для SkillMap (или отдельный пост-вызов) |

## 6) ПДн и макросы

Согласовано:

1. В промпт **не** уходят телефон, ник, email, реальное ФИО.  
2. Вместо них — плейсхолдеры: `{{contact_1}}`, `{{name_1}}`, …  
3. После ответа код **подставляет** реальные значения в текст для тренера.  
4. Этап, даты касаний, обезличенные цифры воронки — можно без макросов.  
5. Заметки — короткая выжимка без лишних ПДн.  
6. **Склонение имён в v1 не делаем**; шаблоны формулируем без падежа («сообщение для {{name_1}}»). Склонение — если на пилоте тексты выглядят криво.

Риск: модель «сломает» плейсхолдер. Парсер должен требовать точный токен; при поломке — fallback без подстановки / перегенерация.

---

## 7) Обучение и навыки

- Не курс, а **микрокарточки** из библиотеки по ходу задач.  
- **SkillMap:** фиксированный список навыков (оффер, касание базы, пост, возражение «дорого», пробная, дожим, follow-up, …).  
- Уровень: онбординг (пара вопросов) + косвенные сигналы (что делает / правит / спрашивает / результаты).  
- После диалога — дешёвый вызов → JSON-сигналы → код обновляет карту.  
- Триггер урока: задача требует навык X, уровень низкий, урок ещё не показан, дневной лимит уроков не исчерпан.

## 8) Модели и стоимость

| Решение | Деталь |
|---------|--------|
| Выбор модели | **Конфиг сценария**, не «модель выбирает модель» |
| Уровни | Дешёвая/быстрая — классификация, извлечение, короткие ответы; сильная — стратегия, совещание |
| Лимит $ | Цифру зафиксировать после 1–2 недель stage; до этого — лимит числа запросов/сутки (как КБЖУ) |
| Ретраи | Ограниченные; без бесконечных циклов tools |

## 9) Общий AI-адаптер

Клиент Caila сейчас в `Modules/Nutrition` (таймаут 5 с, без tools/стриминга).

**Решение (архитектор, блок A, 2026-10-01):**

| Тема | Решение |
|------|---------|
| Где код продаж | Модуль **`LeadGen`** (сценарии, GrowthProfile, задачи, бриф); CRM не раздуваем |
| Где вызов Caila | Общий слой **`Modules/Ai`** (или `App/Ai`): chat, tools, JSON schema, stream, учёт токенов |
| Nutrition | **В том же тикете**, что и вынос адаптера, переводим T-110/КБЖУ на общий слой — без копипасты клиента |
| Пилот к ноябрю | Только **утренний бриф** + адаптер; чат/совещание/обучение — после |
| Зависимость | Перед брифом нужен **T-115** (профиль + план задач), хотя бы rule-based |

ADR зафиксирует имена каталогов и контракт адаптера.

**Блок B (архитектор, 2026-10-01):**

| Тема | Решение |
|------|---------|
| Когда готовим бриф | Крон заранее (утро по **часовому поясу тренера**, `users.timezone`) + пересчёт при открытии раздела, если брифа нет или он устарел |
| UI пилота | Карточка «задачи на сегодня»: задача + «зачем» + «сделано» / «обновить». Без чата и без «переписать текст» |
| Шлюз Caila | **Один URL** `adapters/openai-direct`, model id вида `just-ai/openai-proxy/…`, `just-ai/open-router/…` |
| Доступ | **Белый список** тренеров (конфиг/флаг); аддон и оплата — с I-003 |

**Блок C (архитектор, 2026-10-01):**

| Тема | Решение |
|------|---------|
| Сбой Caila / мусор ответа | **Rule-based бриф** из плана T-115 + заготовки «зачем»; в UI пометка «без ИИ» |
| Когда бриф устарел | Менялись задачи плана **или** важное событие CRM (новая заявка / смена этапа). Событие только ставит флаг «устарел»; пересчёт — при открытии раздела (или по крону) |
| Журнал AiRun / AiTrace | Сценарий, модель, токены, cost, latency, success/fail **+** промпт и ответ **с макросами** (без сырых ПДн); retention **30 дней** |
| Лимит тренера (пилот) | 1 расчёт по крону + до **5** ручных «обновить» / сутки (по TZ тренера) |

Риск по шлюзу: на `openai-direct` проверены только tools (gpt-4o-mini, deepseek). **До миграции Nutrition** LLM-инженер добивает пробы на этом шлюзе: `json_schema`, `json_object`, все 3 модели ансамбля КБЖУ (вкл. qwen), приходит ли `usage.cost`. Если что-то не работает — решение в ADR (временно второй URL только для этой модели).

## 10) Качество (eval)

До prod / при смене промпта:

- Golden set **≥20–30** ситуаций на сценарий (сначала — на `morning_brief`).  
- Автооценка второй моделью + ручной разбор спорных.  
- Критерии: следование guardrails, реалистичность задач под интенсивность, наличие «зачем», корректные макросы, отсутствие ПДн в сыром выводе модели.  
- Feature-тесты кода — **с моками**; live — stage/eval.

---

## 11) Наблюдаемость и fallback

- Логи/трасса: `scenario`, `run_id`, модель, latency, tokens, cost, tool names, success/fail — **без** ключей API и сырых ПДн.  
- Провайдер лёг / лимит: понятный UX + rule-based бриф из шаблона (как «упрощённый помощник» в приоритетах E-006).  
- Runbook: disable сценария / всего чата без падения CRM.
