Сначала JSON Schema (`strict`). Ниже — проверки **после** парсинга. При провале: retry 1 раз (если лимит позволяет) или fallback слоя (техдок §6).

Общие запреты в текстах для тренера — применять ко всем строковым полям ответа (рекурсивно).

---

## 0) Общие проверки текстов

| # | Проверка | Действие |
|---|----------|----------|
| G1 | Нет макросов `{{…}}` | отклонить |
| G2 | Нет шаблонов телефона / email / URL | отклонить |
| G3 | Нет обещаний результата: «гарант», «N клиентов», «через неделю будут заявки» с числом будущего результата (эвристика + стоп-фразы) | отклонить |
| G4 | Нет мед/юр советов: лечен, диагноз, препарат, похудеете на N кг… (стоп-список) | отклонить |
| G5 | Если `clients_new` во входе 0 или null — в текстах нет слов «клиент» в контексте счёта («клиентов: 0», «нет клиентов», «клиентов пока нет») | вырезать предложение или отклонить |
| G6 | Длины полей ≤ max схемы (схема ловит; код дублирует для ясного fallback) | отклонить |
| G7 | Нет жаргона в текстах для тренера: `bottleneck`, `конверси…`, `оффер`, `воронк…`, `лид(ы/ов…)`, `CTA`. «CRM» можно — так называется раздел приложения | в пилоте — журналировать, не отклонять; после пилота решить |

Стоп-фразы G3 / G5 / G7 проверяются **с учётом отрицания**: «не гарантируем результат», «без холодных рассылок», «не требует действий с незнакомыми» — не нарушение (отрицание в пределах 4 слов до совпадения). Эталон — `negated()` в [run_strategic_eval.py](e-014-eval/run_strategic_eval.py).

Имена людей: на стратегическом контуре вход уже без имён контактов; доп. словарь имён — по возможности как в CRM-очистке брифа.

## 1) `intake_extract`

| # | Проверка | Действие |
|---|----------|----------|
| I1 | Все enum-поля ∈ справочнику профиля или null | недопустимое → null + добавить в `unclear` (нормализация) либо отклонить |
| I2 | `services` / `channels` — только allowed, без дублей | нормализовать |
| I3 | Поле заполнено ⇒ его нет в `unclear` | убрать из `unclear` |
| I4 | Обязательная тема null/[] ⇒ есть в `unclear` (specialization, services, goal, old_base, channels, hours, urgency, offer) | добавить в `unclear` |
| I5 | `about` / `offer_note` / `specialization` — без телефонов, email, URL | очистить или отклонить |
| I6 | `goal_clients_per_month` null или 1..50 | иначе null + unclear |

## 2) `diagnose`

| # | Проверка | Действие |
|---|----------|----------|
| D1 | `bottlenecks[].code` ∈ закрытому списку | отклонить |
| D2 | `final_round` ⇒ `questions` пуст | отклонить |
| D3 | `mode=strategy_run` и `data_quality=insufficient` и не `final_round` ⇒ `questions` не пуст | отклонить / retry |
| D4 | `mode=strategy_run` и `data_quality=sufficient` ⇒ `questions` отрезать до [] (не отклонять весь ответ) | нормализовать |
| D5 | `questions` ≤ 3; у каждого 2–5 `options`; `key` уникальны | отклонить |
| D6 | `profile_field` задан ⇒ `profile_field` ∈ `askable_fields`, `allow_free_text=false` и options ⊆ справочник поля. Основная защита — схема, собранная под запрос ([отчёт](e-014-strategic-eval-v1.md) §5); проверка — страховка | выбросить вопрос (не весь ответ) |
| D7 | `profile_field=null` ⇒ `allow_free_text=true` | иначе выставить true или отклонить |
| D8 | `profile_change_proposals` — только `field` ∈ `mismatch_flags`; значения ∈ справочнику | отбросить лишние |
| D9 | `observations[].topic` ∈ списку | отклонить |
| D10 | `mode=strategy_run` ⇒ `profile_change_proposals` обычно []; если не пуст без флагов — отбросить | нормализовать |
| D11 | Тон не проверяем эвристикой жёстко; G3–G5 обязательны | |
| D12 | Коды узких мест не противоречат анкете: `no_base` только при `old_base_size` none / lt10; `base_untouched` только при 10_30 / gt30; вместе нельзя | выбросить противоречащий код (если остался ≥ 1) |
| D13 | `mode=weekly` и во входе есть facts / week_plan_performance ⇒ `observations` ≥ 1 | журналировать (не отклонять) |
| D14 | Тексты на «вы»: `strengths` / `opportunities` / `assumptions` не начинаются с «Тренер…» | журналировать |

| P1 | `strategies` длина 2..3 | отклонить |

## 4) `decompose`

| # | Проверка | Действие |
|---|----------|----------|
| C1 | `items` 1..10; `key` уникальны | отклонить |
| C2 | `type` ∈ `allowed_types` / фиксированный список `strategy.*` | отклонить пункт / ответ |
| C3 | `minutes` 5..60 | отклонить |
| C4 | `frequency.kind=times_per_week` ⇒ `times_per_week` 1..7; иначе `times_per_week` null | отклонить |
| C5 | Сумма минут недели ≤ `weekly_minutes_cap` (once=1, daily=7, times_per_week=N) | обрезать хвост пунктов или отклонить → fallback шаблонов |
| C6 | `hint` ≤ 200, не пустой (можно один пробел? → требуем ≥ 10 символов осмысленного текста) | отклонить пункт |
| C7 | `phase=weekly` ⇒ `milestones` можно []; `phase=first_plan` ⇒ milestones ≥ 1 | отклонить |
| C8 | `success_criteria.metric` ∈ tasks_done, contacts_added, dialogs_started, leads_new | отклонить |
| C9 | `task_type` в критерии null или ∈ strategy.* | отклонить |
| C10 | Нет `crm_contact_id` / имён в title | отклонить |
| C11 | G3–G5 | отклонить |

## 5) `review`

| # | Проверка | Действие |
|---|----------|----------|
| R1 | `status` и `recommendation` из enum | схема |
| R2 | Если `weeks_elapsed < 1` и модель не `too_early` — можно принять, но код при правилах сам ставит `too_early` без ИИ | оркестратор |
| R3 | `status=failed` при `clients_new=0` и вехи/задачи не провалены по действиям — **отклонить** (нельзя failed только из‑за клиентов) | отклонить / retry |
| R4 | `clients_new=0` ⇒ G5 на всех текстах | отклонить |
| R5 | `what_works` ≥ 1 | отклонить |
| R6 | G3–G4 | отклонить |
| R7 | `clients_new > 0` ⇒ клиенты названы в `what_works` (решение PO: не критерий, но показываем; «клиентов: 0» — никогда) | код дописывает пункт «Новых клиентов: N» первым, retry не нужен |

## 6) Контракты входа (что код обязан передать)

Чтобы проверки и промпты работали, оркестратор кладёт в user JSON:

| Сценарий | Обязательные поля входа |
|----------|-------------------------|
| intake | `story`, `allowed` |
| diagnose | `mode`, `final_round`, `round`, `profile`, агрегаты, `mismatch_flags` (хотя бы []), `askable_fields` (пустые поля анкеты + `mismatch_flags`), `profile_allowed` — только для `askable_fields` |
| propose | `profile`, `diagnosis`, `knowledge_cards` |
| decompose | `phase`, `strategy`, `profile`, `default_tasks`, `allowed_types`, `weekly_minutes_cap` |
| review | `strategy`, `milestones`, `facts` (с `clients_new`), `plan_performance`, `weeks_elapsed` |

## 7) Передать архитектору / разработчику

1. Этот список — канон содержательных проверок для `Strategic/*Validator` (имена на усмотрение архитектора).
