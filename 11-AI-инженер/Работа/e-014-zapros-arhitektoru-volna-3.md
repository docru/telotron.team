## Зачем

Пилот E-010 (утренний бриф) в коде. Целевая архитектура ИИ-РОП спроектирована (`Работа/Агенты/`). Волна 3: продуктовые решения приняты; нужны **решения по модели данных и границам модулей**, прежде чем проектировать стратегический слой (волна 4) и нарезать тикеты.

## Уже решено (продукт + LLM-инженер)

| Тема | Решение |

| Лимит исчерпан | Fallback без ИИ + короткая пометка тренеру |

### Лимиты (подтверждено)

| Слой | Лимит |
|------|-------|
| Операционный | 6 вызовов / сутки (как сейчас) |
| Стратегический | ≤ 5 вызовов **на цикл**; ≤ 2 цикла / неделю |
| Инструментальный | 20 вызовов / сутки |
| Образование / поддержка | без своего лимита (шаблоны кода) |
| Страховка | потолок **3 ₽ / сутки** на тренера по всем слоям LeadGen |

Сейчас счётчик операционного лимита — в `MorningBriefCalculator` по `ai_runs` где `scenario=leadgen.morning_brief`. Страховочный ₽-потолок потребует надёжного `cost_rub` в `ai_runs` (у gpt-4o-mini Caila не всегда отдаёт `usage.cost` — считаем по прайсу; детали в T-138).

## Вопросы к архитектору

### 1. Задачи стратегии — куда писать?

Целевая модель: Декомпозер создаёт задачи, которые попадают в бриф вместе с `plan` и `crm_signal`.

**Предложение LLM-инженера:** расширить `leadgen_tasks`:

- новый `source = strategy` (enum);
- поля связи со стратегией / вехой (например `strategy_id`, опционально `milestone_id`);
- тот же `dedupe_key`, тот же путь в бриф через `BriefCandidatePreparer` (новый tier/rank).

**Альтернатива:** отдельная таблица `leadgen_strategy_tasks` + merge при сборке кандидатов — риск дублей и двух «сделано».

**Нужно от тебя:** один список задач или два? Минимальный набор полей для `source=strategy`? Нужен ли ADR-дополнение к ADR-011?

### 2. Черновик заметки CRM (HITL)

Продукт: ИИ пишет текст → тренер правит / подтверждает → запись через существующий `CrmContactService::addNote` с `author_type=trainer`.

**Предложение:** хранить черновик в LeadGen (например `leadgen_drafts`: contact_id, kind=note|message, body с макросами, status=pending|accepted|discarded, ai_run_id). В CRM — только после accept, штатным сервисом. `Modules/Ai` по-прежнему только chat + journal.

**Нужно от тебя:** ок ли `leadgen_drafts` в LeadGen? Или черновик — сущность CRM? Меняем ли ADR-011 («ИИ не пишет в CRM») явным исключением «только через HITL-черновик»?

### 3. Таблица сигналов тренера

Один контур для: весов скоринга, карты компетенций, поддержки (уровни 0–1).

**Предложение:** новая таблица в LeadGen, например `leadgen_trainer_signals`:

| Поле (черновик) | Смысл |
|-----------------|--------|
| trainer_id, local_date | кто / когда |
| kind | `brief_item_done` · `brief_item_postpone` · `brief_item_reject` · `care_thanks_no` · `care_shown` · … |
| brief_id / task_id | nullable, связь |
| payload JSON | минимум контекста без сырых ПДн |
| created_at | |

Не поля в `ai_runs` (другой retention и смысл) и не размазывание по `leadgen_morning_briefs`.

API: POST реакций с брифа / карточки поддержки; чтение — внутренним сервисам скоринга и care.

**Нужно от тебя:** имя/схема таблицы ок? Нужен ли отдельный ADR или достаточно дополнения техдока LeadGen? Retention сигналов (предложение: 1 год, как метаданные ai_runs)?

### 4. Оркестратор — где живёт код?

**Предложение:** namespace / сервисы внутри `app/Modules/LeadGen` (например `LeadGen/Orchestration` или расширение существующих `MorningBrief*` + новые cycle-сервисы). Не новый top-level `Modules/SalesAi`, не внутри `Modules/Ai` (ADR-010: оркестрация у потребителя).

**Нужно от тебя:** подтвердить границу модуля; если нужен отдельный модуль — обосновать сейчас, пока нет кода.

### 5. Счётчики лимитов по слоям

Сейчас: count `ai_runs` по одному `scenario` за локальные сутки.

При раздельных лимитах нужны:

- маппинг `scenario` → слой (oper / strategy / tools);
- для стратегии — ещё окно «цикл» и «неделя», не только сутки;
- ₽-потолок по сумме `cost_rub` за сутки (с fallback-расчётом по токенам × прайс).

**Предложение:** считать из `ai_runs` + конфиг `leadgen.limits.{layer}`; отдельную таблицу счётчиков не заводить, пока не упрёмся в производительность. Цикл стратегии — сущность `leadgen_strategy_runs` (или `strategy_runs`) с `started_at` / `finished_at` / `ai_run_ids`.

**Нужно от тебя:** ок ли «только ai_runs + strategy_runs»? Где хранить прайс для расчёта cost (config vs таблица)?

### 6. Нужны ли ADR сейчас?

| Кандидат | Зачем |
|----------|--------|
| Дополнение ADR-011 | `source=strategy`, HITL-черновики, реакции, лимиты по слоям |
| Новый ADR «ИИ-РОП / оркестратор» | если граница модуля или граф циклов достаточно крупны |
| Не трогать ADR-010 | адаптер остаётся транспортом |

**Нужно от тебя:** один доп. к ADR-011 vs новый ADR vs оба.

### 7. Глоссарий и правила именования

Добавлено архитектором 2026-10-08 · обновлено 2026-10-10. Имена таблиц и классов из вопросов 1–5: [sales-глоссарий-и-нейминг.md](../../../_telotron.ru/docs/Техдок/03-модули/sales-глоссарий-и-нейминг.md) (proposed).

Решено: модуль помощника — **Sales** (бывший LeadGen); **Crm** остаётся верхним модулем рядом (несколько писателей). Каталоги разделов Sales = слои (`Operational/`, `Strategic/`, `Tools/`, `Education/`); разделы общаются через сервисы; RAG-техника — в `Modules/Ai`; поддержка — `Care/`. Скоринг — механизм общий, факторы/веса у слоя. Группировка областей продукта — в `app/Modules/README.md`.

Следствия: таблицы помощника с префиксом `sales_`; слой для лимитов — `sales.{operational|strategic|tools}.…`; бриф в API — `/me/sales/brief`, код — в `Operational/`. В предложениях ниже имена `leadgen_*` читать как целевые `sales_*` после тикета переименования.

## Ответ архитектора (2026-10-10)

Канон имён: [sales-глоссарий-и-нейминг.md](../../../_telotron.ru/docs/Техдок/03-модули/sales-глоссарий-и-нейминг.md). Ниже имена **целевые** (`sales_*`); в коде пилота пока `leadgen_*` до тикета переименования.

### 1. Задачи стратегии — куда писать?

**Принято:** один список `sales_tasks` (сейчас `leadgen_tasks`).

- `source = strategy`
- поля: `strategy_id` (обязателен при этом source), `milestone_id` (nullable)
- тот же `dedupe_key`, тот же путь в бриф через кандидатов
- отдельную `sales_strategy_tasks` **не** заводим

Дополнение к ADR-011: да, коротко про `source=strategy` (см. п. 6).

### 2. Черновик заметки CRM (HITL)

**Принято:** черновик в Sales — `sales_drafts` (`contact` → `crm_contact_id`, `kind` note|message, тело, статус, `ai_run_id`). В CRM пишет только тренер после accept штатным `CrmContactService`. Не сущность CRM.

В ADR-011 уточнить: «ИИ не пишет в CRM» сохраняется; исключение только через HITL-черновик + явный accept тренера.

Отдельная `sales_tool_runs` **не нужна** на старте: хватает `ai_runs` + `sales_drafts` (и при необходимости сигналов). Заведём, если появятся инструменты без черновика с долгим своим состоянием.

### 3. Таблица сигналов тренера

**Принято:** `sales_trainer_signals` в Sales, раздел `TrainerSignals/`.

- виды в духе `brief_item.done` · `brief_item.postponed` · `brief_item.rejected` · `care.shown` · `care.declined` · `lesson.*` (точка в значении, не подчёркивание)
- retention: **1 год**, как метаданные рядом с журналом ИИ
- отдельный ADR не обязателен — схема в техдоке Sales + строка в доп. к ADR-011

### 4. Оркестратор — где живёт код?

**Принято:** внутри `app/Modules/Sales/Orchestration/` (не новый top-level модуль, не внутри `Modules/Ai`). Согласуется с ADR-010: оркестрация у потребителя.

### 5. Счётчики лимитов по слоям

**Принято:** считать из `ai_runs` + конфиг `sales.limits.{operational|strategic|tools}`; отдельную таблицу счётчиков не заводить.

- слой = сегмент сценария `sales.{operational|strategic|tools}.…`
- цикл стратегии — сущность `sales_strategy_runs` (`started_at` / `finished_at` / связи с `ai_run`)
- прайс для fallback `cost_rub`: **config** (версия прайса в конфиге/доке), не таблица, пока прайс меняется редко

### 6. Нужны ли ADR сейчас?

**Принято:** одно **дополнение к ADR-011** (source=strategy, HITL-черновики, сигналы, лимиты по слоям, переименование модуля LeadGen→Sales в каноне). Новый ADR «оркестратор» **не** нужен: граница модуля уже ясна. ADR-010 не трогаем. ADR-006 (CRM) не склеиваем с Sales.
