# План разработки модуля

## Логика плана

План следует **сверху вниз**: от пилота к архитектуре, от согласования к детальному проектированию слоёв, от конкретики к разработке. Каждая волна даёт результат, который становится фундаментом для следующей. Критерий перехода — явный, а не «кажется, готово».

**Ключевой принцип:** проектируем сверху вниз — от того, что определяет вход, к тому, что его использует.

---

## Волна 1. Пилот (сделано)

**Что уже есть:** утренний бриф — код собирает задачи, ИИ выбирает 1–3 и пишет «зачем». Работает на gpt-4o-mini, с валидацией, fallback, лимитами, логированием.

**Статус:** завершено. Это фундамент, на котором строится всё остальное.

**Что важно сохранить:**
- Принцип «код решает, ИИ объясняет»
- Валидация + fallback
- Логирование каждого вызова
- Лимиты и бюджет
- PII-минимизация через макросы

**Критерий перехода:** работает, проверено на 25 ситуациях.

---

## Волна 2. Общая архитектура многоагентной системы (спроектировано)

**Что уже есть:** описание шести компонентов — оркестратор, стратегический, операционный, инструментальный, образовательный слои, логирование и обучение. Плюс сквозные механизмы — адаптация и скоринг.

**Статус:** концептуально спроектировано.

**Что даёт:**
- Целостная картина
- Понимание ролей ИИ и кода в каждом слое
- Основа для согласования

**Что ещё не сделано:**
- Нет привязки к реальным инструментам и API
- Нет конкретных формул, весов, промптов
- Нет плана реализации по этапам

**Критерий перехода:** есть целостная картина, понятны роли и связи.

## Волна 3. Согласование с существующей архитектурой

**Задача:** встроить спроектированную систему в то, что уже есть — CRM, план продвижения, существующие инструменты, инфраструктура.

### 3.1. Инвентаризация существующего

| Что проверить | Зачем |
|---|---|
| Какие API есть у CRM | Понять, откуда брать задачи и куда писать результаты |
| Как устроен план продвижения | Понять, как стратегия будет с ним связана |
| Какие инструменты уже есть | Понять, что можно переиспользовать |
| Какая инфраструктура | Понять, где хостить, где хранить логи |
| Какие ограничения | Понять, что нельзя делать |

### 3.2. Определение точек интеграции

| Слой | Читает | Пишет |
|---|---|---|
| Стратегический | Профиль, метрики, CRM | Стратегия, задачи |
| Операционный | CRM, стратегия, календарь | Бриф, статусы задач |
| Инструментальный | CRM, профиль лида | Черновики, анализ |
| Образовательный | Логи, карта компетенций | Подсказки, режимы |
| Логирование | Все вызовы | Логи, метрики |

### 3.3. Согласование с оркестратором

- Где он живёт в существующей архитектуре
- Как он запускается (cron, события)
- Как взаимодействует с существующими модулями
- Какие лимиты и бюджет контролирует

### 3.4. Проверка на конфликты

| Что проверить | Риск |
|---|---|
| Дублирование данных | Одна задача в двух местах |
| Конфликт лимитов | Существующие лимиты vs новые |
| Конфликт PII-политик | Что можно передавать в модель |
| Конфликт ролей | Кто отвечает за что |

**Критерий перехода:** все точки интеграции определены, оркестратор встроен, конфликты разрешены.

## Волна 4. Детальное проектирование стратегического слоя

**Задача:** детально спроектировать стратегический слой — он определяет вход для всех остальных.

**Почему первым:** стратегический слой решает, какие задачи попадут в операционный, какие навыки нужны тренеру, какие критерии успеха. Без него нельзя проектировать остальные слои.

### 4.1. Диагност

| Артефакт | Что содержит |
|---|---|
| Вход | Профиль, метрики, история задач, текущая стратегия, карта компетенций |
| Выход | Схема диагноза: strengths, bottlenecks, hypotheses, opportunities, skill_gaps, data_quality |
| Промпт | Роль, инструкции, схема, ограничения |
| Логика анализа | Как сравнивать метрики, как искать паттерны |
| Валидация | Проверки кода после ответа ИИ |
| Fallback | Что делать при сбое |

### 4.2. Стратег

| Артефакт | Что содержит |
|---|---|
| Вход | Диагноз, профиль, RAG-методики, few-shot примеры, карта компетенций |
| Выход | Схема: 2–3 стратегии + рекомендация |
| Промпт | Роль, инструкции, схема, ограничения |
| RAG-запросы | Как формируются запросы к базе методик |
| Логика генерации | Как комбинируются методики в стратегии |
| Валидация | Проверки кода |
| Fallback | Что делать при сбое |

### 4.3. Декомпозер

| Артефакт | Что содержит |
|---|---|
| Вход | Выбранная стратегия, профиль, шаблоны задач, карта компетенций |
| Выход | Схема: milestones, tasks, success_criteria, micro_learning |
| Промпт | Роль, инструкции, схема, ограничения |
| Логика декомпозиции | Как разбивать стратегию на задачи |
| Валидация | Проверки кода |
| Fallback | Что делать при сбое |

### 4.4. Монитор

| Артефакт | Что содержит |
|---|---|
| Вход | Стратегия, критерии успеха, метрики, история выполнения |
| Выход | Схема: status, explanation, what_works, what_doesnt, recommendation |
| Промпт | Роль, инструкции, схема, ограничения |
| Логика оценки | Как сравнивать метрики с критериями |
| Валидация | Проверки кода |
| Fallback | Что делать при сбое |

### 4.5. Цикл стратегического слоя

| Артефакт | Что содержит |
|---|---|
| Триггеры | Календарь, провал метрик, смена предложения, ручной запрос, накопление задач |
| Последовательность | Диагност → Стратег → выбор → Декомпозер |
| Точки human-in-the-loop | Выбор стратегии тренером |
| Связь с операционным | Как задачи передаются в бриф |
| Связь с логированием | Что пишется в `strategy_runs` |

### 4.6. RAG-база методик

| Артефакт | Что содержит |
|---|---|
| Структура карточки | Поля: тип, название, содержание, условия, ограничения, ресурсы |
| Уровни | Алгоритмы, тактики, шаблоны, ограничения |
| Механика поиска | Гибридный поиск, ранжирование |
| Обновление | Как добавляются новые методики |

### 4.7. Few-shot примеры

| Артефакт | Что содержит |
|---|---|
| Формат | Профиль, диагноз, стратегия, результат, вывод |
| Отбор | Как выбираются релевантные примеры |
| Обновление | Как добавляются новые |

### 4.8. Оркестрация стратегического цикла

| Артефакт | Что содержит |
|---|---|
| Граф вызовов | Последовательность агентов |
| Обработка сбоев | Что делать при падении каждого агента |
| Лимиты | Сколько вызовов на цикл |
| Логирование | Что пишется |

**Критерий перехода:** стратегический слой детально спроектирован, понятно, какие задачи он выдаёт в операционный, какие навыки требует, какие критерии задаёт.

## Волна 5. Детальное проектирование операционного, инструментального и образовательного слоёв

**Задача:** детально спроектировать три слоя, которые работают в связке и зависят от стратегического.

**Почему в связке:** операционный получает задачи из стратегического, инструментальный вызывается из операционного, образовательный пронизывает оба.

### 5.1. Операционный слой

| Артефакт | Что содержит |
|---|---|
| Источники задач | CRM, стратегия, календарь — что именно берётся |
| Сбор | Как собираются задачи, дедупликация, нормализация |
| Скоринг | Факторы, веса, формула, пороги отсечения |
| Топ-N | Сколько задач передаётся в ИИ |
| Исполнитель | Промпт, схема выхода, ограничения |
| Валидация | Проверки кода после ответа ИИ |
| Сборка брифа | Подстановка имён, фиксация версии |
| Дельта-режим | Как обрабатываются изменения |
| Обратная связь | Кнопки, сигналы, куда уходят |
| Fallback | Что делать при сбое |
| Оркестрация | Граф вызовов, лимиты, логирование |

### 5.2. Инструментальный слой

| Артефакт | Что содержит |
|---|---|
| Список инструментов | Скриптовые и ИИ-инструменты |
| Связь с задачами | Какой инструмент для какой задачи |
| Черновик сообщения | Промпт, вход, выход, валидация |
| Анализ ответа | Промпт, вход, выход, валидация |
| Разбор правок | Промпт, вход, выход, валидация |
| Два режима | «Сделай за меня» / «Покажи, как» — как выбирается |
| Human-in-the-loop | Где тренер утверждает |
| Логирование | Что пишется в `tool_runs` |
| Fallback | Что делать при сбое |

### 5.3. Образовательный слой

| Артефакт | Что содержит |
|---|---|
| Карта компетенций | Список навыков, уровни, правила обновления |
| Форматы микро-обучения | Пример, принцип, чек-лист, разбор |
| Связь с задачами | Когда показывается подсказка |
| Связь с инструментами | Как выбирается режим |
| Логирование | Что пишется в `micro_learning` |
| Правила | Не блокирует, только предлагает |

### 5.4. Связка трёх слоёв

| Артефакт | Что содержит |
|---|---|
| Поток задач | Стратегия → операционный → инструментальный |
| Поток подсказок | Образовательный → операционный → инструментальный |
| Поток обратной связи | Тренер → логирование → обучение |
| Точки human-in-the-loop | Где тренер принимает решения |

### 5.5. Оркестрация трёх слоёв

| Артефакт | Что содержит |
|---|---|
| Граф вызовов | Последовательность агентов |
| Обработка сбоев | Что делать при падении каждого агента |
| Лимиты | Сколько вызовов в сутки |
| Логирование | Что пишется |

**Критерий перехода:** три слоя детально спроектированы, понятно, как они работают вместе.

## Принципы, которые важно сохранить

1. **Не перескакивать волны.** Конкретика без согласования — переделка. Разработка без конкретики — хаос.
2. **Критерий перехода — явный.** Не «кажется, готово», а «все точки интеграции определены».
3. **Проектировать сверху вниз.** Стратегический слой первым — он определяет вход.
4. **Пилот — фундамент.** Не ломать то, что работает.
5. **Код решает, ИИ объясняет.** Сохраняется на всех волнах.
6. **Логирование — с первого дня.** Без него нет обучения.
7. **Fallback — обязателен.** Тренер не остаётся без результата.
8. **Human-in-the-loop — на ключевых решениях.** Выбор стратегии, отправка сообщений.

**Главная идея:** вы идёте правильным путём — от общего к частному, сверху вниз. Каждая волна даёт результат, который становится фундаментом для следующей. Не торопитесь перескакивать: конкретика без согласования — это переделка, а разработка без конкретики — это хаос.
