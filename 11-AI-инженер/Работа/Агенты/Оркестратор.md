# Оркестратор: полное описание

## 1. Что это такое

**Оркестратор** — это центральный управляющий компонент системы, который координирует работу всех агентов и слоёв. Это **не ИИ**, а детерминированный код. Его задача — решать, **какой агент, когда, с каким контекстом и в какой последовательности запускать**, а также **что делать при сбоях**.

**Метафора:** если агенты — это музыканты, то оркестратор — дирижёр. Он не играет сам, но без него оркестр превращается в какофонию.

**Ключевой принцип:** оркестратор принимает **координационные** решения, но не **содержательные**. Он не решает, какая стратегия лучше — это делает Стратег. Он решает, когда запустить Стратега и что передать ему на вход.

---

## 2. Зачем он нужен

В системе пять слоёв и несколько агентов. Без оркестратора они существовали бы разрозненно:

- Кто решает, что пора запускать стратегический цикл?
- Кто определяет, какого агента вызвать первым?
- Кто решает, что делать, если Диагност упал?
- Кто следит за лимитами вызовов и бюджетом?
- Кто решает, когда бриф устарел и его нужно пересчитать?
- Кто гарантирует, что Декомпозер не запустится до выбора стратегии?

Всё это — **не задача ИИ**. Это задача координации. Её решает оркестратор.

---

## 3. Функции оркестратора

### 3.1. Определяет триггеры запуска

Оркестратор знает, **когда** запускать каждый цикл.

**Стратегический цикл:**

| Триггер | Условие |
|---|---|
| Календарь | Раз в 2–4 недели с даты последнего пересмотра |
| Провал метрик | Конверсия упала ниже порога |
| Смена предложения | Тренер изменил услуги, цены, аудиторию |
| Ручной запрос | Тренер нажал «Пересмотреть стратегию» |
| Накопление задач | N невыполненных задач из стратегии |

**Операционный цикл:**

| Триггер | Условие |
|---|---|
| Календарь | Ежедневно в 07:00 по часовому поясу тренера |
| Новые данные | Новая заявка, ответ лида, изменение в CRM |
| Ручной запрос | Тренер нажал «Обновить бриф» |

**Инструментальный слой:**

| Триггер | Условие |
|---|---|
| Открытие задачи | Тренер открыл задачу → предложить инструменты |
| Редактирование | Тренер отредактировал черновик → запустить «Разбор» |
| Запрос тренера | Тренер нажал «Помоги написать» |

### 3.2. Определяет последовательность вызовов

Оркестратор знает **граф вызовов** и не позволяет нарушать порядок.

**Стратегический цикл:**
```
Триггер
  → Сбор контекста (код)
  → Диагност (ИИ)
  → [проверка: диагноз валиден?]
      → нет: уведомить, стоп
      → да: продолжить
  → Стратег (ИИ)
  → [проверка: стратегии валидны?]
      → нет: повторить 1 раз, затем fallback
      → да: показать тренеру
  → [ожидание выбора тренера]
  → Декомпозер (ИИ)
  → [проверка: задачи валидны?]
      → нет: fallback на шаблоны
      → да: сохранить
  → Задачи в операционный слой
```

**Операционный цикл:**
```
07:00
  → Сбор задач (код)
  → Нормализация (код)
  → Скоринг (код)
  → Отсечение (код)
  → [проверка: есть задачи?]
      → нет: бриф «сегодня задач нет»
      → да: продолжить
  → Исполнитель (ИИ)
  → Валидация (код)
  → [проверка: ответ валиден?]
      → нет: fallback «без ИИ»
      → да: собрать бриф
  → Фиксация версии
  → Отправка тренеру
```

**Дельта-режим:**
```
Событие: новые данные
  → [проверка: бриф уже отправлен?]
      → нет: обновить бриф
      → да: создать дельту
  → [проверка: лимит вызовов?]
      → превышен: отложить до следующего дня
      → нет: вызвать Исполнителя для дельты
  → Добавить дельту к брифу
```

### 3.3. Управляет контекстом

Оркестратор решает, **что передать** каждому агенту. Он не даёт агенту лишнего — только то, что нужно для его задачи.

| Агент | Что получает | Что НЕ получает |
|---|---|---|
| **Диагност** | Профиль, метрики, история задач, текущая стратегия | RAG-методики, few-shot примеры |
| **Стратег** | Диагноз, профиль, RAG-методики, few-shot примеры | Всю историю задач, сырые метрики |
| **Декомпозер** | Выбранная стратегия, ресурсы тренера, шаблоны задач | Диагноз, RAG-методики |
| **Исполнитель** | Топ-N задач, профиль, стиль, метрики воронки | Всю историю, RAG-методики |
| **Инструменты** | Контекст задачи, профиль лида, стиль тренера | Данные других лидов |

**Зачем:** меньше контекста — меньше шума, ниже стоимость, выше точность.

### 3.4. Обрабатывает сбои

Это одна из главных функций. Оркестратор знает, **что делать, если агент упал**.

| Сбой | Действие |
|---|---|
| **Диагност упал** | Уведомить тренера, не запускать Стратега |
| **Стратег упал** | Повторить 1 раз, затем fallback «продолжить текущую стратегию» |
| **Декомпозер упал** | Задачи не создаются, уведомление, fallback на шаблоны |
| **Исполнитель упал** | Бриф по правилам с пометкой «без ИИ» |
| **Инструмент упал** | Предложить шаблонный вариант |
| **Провайдер недоступен** | Fallback на правила, логирование |
| **Валидация не прошла** | Отбраковка, fallback, логирование инцидента |

**Принцип:** тренер никогда не остаётся без результата. Даже при полном сбое ИИ — бриф по правилам.

### 3.5. Следит за лимитами и бюджетом

Оркестратор — «бухгалтер» системы.

| Параметр | Значение |
|---|---|
| Лимит вызовов | 6 на тренера в сутки |
| Стоимость вызова | ~0,04 ₽ |
| Бюджет на тренера в сутки | ≤ 0,22 ₽ |

**Что делает:**
- Считает вызовы перед каждым запуском
- Не даёт превысить лимит
- При исчерпании — переключает в режим «без ИИ» до следующего дня
- Логирует каждый вызов в `ai_runs`

### 3.6. Управляет состоянием

Оркестратор знает **текущее состояние системы**:

| Состояние | Что означает |
|---|---|
| Активная стратегия | Какая стратегия сейчас работает |
| Зафиксированный бриф | Какой бриф отправлен сегодня |
| Выполненные задачи | Что уже сделано |
| Изменения данных | Что изменилось с утра |
| Лимиты | Сколько вызовов использовано |

**Зачем:** чтобы не пересчитывать то, что уже посчитано, и не ломать картину тренера.

### 3.7. Приоритизирует конфликты

Когда задачи из CRM и стратегии конфликтуют — оркестратор решает по правилам:

| Ситуация | Решение |
|---|---|
| «Горячий» лид из CRM vs задача из стратегии | CRM в приоритете |
| Задача из стратегии с близким дедлайном vs рутинная из CRM | Стратегия в приоритете |
| Две задачи на одного лида | Объединить или выбрать одну |
| Задача требует навыка, которого нет | Понизить приоритет или добавить обучающий шаг |

**Конфликты решает код, не ИИ.**

---

## 4. Чего оркестратор НЕ делает

Важно понимать границы:

| Не делает | Кто делает |
|---|---|
| Не принимает содержательных решений | Стратег, тренер |
| Не генерирует текст | Исполнитель, инструменты |
| Не обучается | Слой обучения |
| Не валидирует ответы | Валидатор (код) |
| Не работает с данными напрямую | Модули сбора |
| Не пишет промпты | Промпт-менеджер |
| Не хранит данные | БД |

**Оркестратор — это координатор, а не исполнитель.**

## 5. Техническая реализация

### 5.1. Варианты

**Простой (для MVP):**
Набор функций в коде, вызываемых по cron или webhook.

```python
def run_daily_brief(trainer_id):
    # Проверка лимитов
    if not check_limits(trainer_id):
        return fallback_brief(trainer_id)
    
    # Сбор задач
    tasks = collect_tasks(trainer_id)
    if not tasks:
        return empty_brief(trainer_id)
    
    # Скоринг и отсечение
    scored = score_tasks(tasks)
    top = cut_off(scored)
    
    # Вызов ИИ
    try:
        result = run_executor(top, trainer_id)
    except Exception as e:
        log_error(e)
        return fallback_brief(top)
    
    # Валидация
    if not validate(result):
        log_validation_failure(result)
        return fallback_brief(top)
    
    # Сборка и фиксация
    brief = assemble_brief(result, trainer_id)
    save_brief(trainer_id, brief)
    return brief
```

**Продвинутый (для production):**
Графовая оркестрация (LangGraph, Temporal). Даёт:
- Явную визуализацию потока
- Устойчивость к падениям (durable execution)
- Приостановку и возобновление
- Трассировку каждого шага

### 5.2. Компоненты

| Компонент | Зачем |
|---|---|
| **Планировщик** | Cron для ежедневных запусков |
| **Очередь событий** | Webhook для реакции на данные |
| **Хранилище состояния** | Знать, что происходит сейчас |
| **Логирование** | Трассировка каждого вызова |
| **Лимиты** | Контроль вызовов и бюджета |
| **Валидатор** | Проверка ответов ИИ |
| **Fallback** | Работа без ИИ при сбое |

```

07:01 — Вызывает Исполнителя

07:01 — Запускает валидацию
        Проверка пройдена
        Собирает бриф, фиксирует версию, отправляет

        Лимит: 2/6

        Логирует сигнал, обновляет CRM

18:00 — Проверяет триггеры стратегического цикла
        Метрики в норме → нет

23:59 — Агрегирует метрики за день
        Сохраняет в metrics_daily
        Сбрасывает счётчик вызовов
```

## 8. Принципы работы

1. **Код, не ИИ.** Оркестратор — детерминированный.
2. **Координация, не содержание.** Не решает «что», решает «когда» и «как».
3. **Безопасность по умолчанию.** При сбое — fallback, не ошибка.
4. **Лимиты — закон.** Не превышать бюджет.
5. **Состояние — истина.** Не пересчитывать то, что уже посчитано.
6. **Логирование — обязательно.** Каждый шаг трассируется.
7. **Тренер не остаётся без результата.** Даже при полном сбое ИИ.

## 9. Что это значит для реализации

**Минимальный MVP:**

| Компонент | Реализация |
|---|---|
| Планировщик | Cron (ежедневно в 07:00) |
| Триггеры | Календарь + webhook на события CRM |
| Последовательность | Функции в коде |
| Контекст | Сборка контекста для каждого агента |
| Сбои | Try/except + fallback |
| Лимиты | Счётчик в БД + проверка перед вызовом |
| Состояние | Таблица `system_state` |
| Логирование | `ai_runs`, `strategy_runs`, `tool_runs` |

**Что можно отложить:**
- Графовую оркестрацию (LangGraph)
- Durable execution
- Автоматические триггеры стратегического цикла
- Сложную приоритизацию конфликтов

**Что нельзя откладывать:**
- Проверку лимитов
- Fallback при сбое
- Логирование
- Разделение «код решает / ИИ объясняет»
- Фиксацию состояния

## Итог

| Аспект | Решение |
|---|---|
| **Что это** | Центральный управляющий компонент, код |
| **Задача** | Координировать агентов и слои |
| **Функции** | Триггеры, последовательность, контекст, сбои, лимиты, состояние, конфликты |
| **Не делает** | Не принимает содержательных решений, не генерирует, не обучается |
| **Роль ИИ** | Нет |
| **Реализация** | От cron + функций до графа (LangGraph) |

**Ключевой принцип:** оркестратор — это **дирижёр**, а не музыкант. Он не играет, но без него оркестр превращается в какофонию. В вашей системе он гарантирует, что каждый агент вызывается вовремя, с нужным контекстом, в рамках лимитов и с fallback при сбое.
