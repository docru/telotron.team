# Стратегический слой: полное описание

## 1. Назначение

**Стратегический слой** — это «мозг» системы. Он отвечает на вопрос **«куда идём и почему»**, в отличие от операционного слоя, который отвечает «что делать сегодня».

**Задача слоя:** раз в 2–4 недели (или по триггеру) пересмотреть ситуацию тренера, выявить узкие места, предложить 2–3 стратегии, помочь выбрать одну, разбить её на задачи и отслеживать прогресс.

**Ритм работы:** медленный. Это не ежедневная рутина, а периодический пересмотр. Стратегия не меняется каждый день — иначе тренер не успеет её реализовать.

**Роль ИИ:** высокая. Здесь нужна интерпретация, синтез, генерация вариантов и обоснование. Код только валидирует и структурирует.

---

## 2. Место в архитектуре

```
┌─────────────────────────────────────────────────────────────┐
│                      ОРКЕСТРАТОР                            │
│  Решает: когда запускать, кого вызывать, что передать       │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   СТРАТЕГИЧЕСКИЙ СЛОЙ                       │
│                                                             │
│  Диагност → Стратег → [выбор тренера] → Декомпозер          │
│                              ↓                              │
│                          Монитор                            │
│                                                             │
│  Результат: стратегия + задачи + критерии успеха            │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   ОПЕРАЦИОННЫЙ СЛОЙ                         │
│  Получает задачи из стратегии и ставит их в бриф            │
└─────────────────────────────────────────────────────────────┘
```

**Связи:**
- **Вход:** профиль тренера, метрики, история задач, RAG-методики, few-shot примеры.
- **Выход:** стратегия, задачи, критерии успеха.
- **Обратная связь:** сигналы от тренера (выполнено/отложено/отклонено) → Монитор → пересмотр.

---

## 3. Агенты слоя

Слой состоит из **четырёх агентов**, каждый со своей ролью.

| Агент | Роль | Когда вызывается |
|---|---|---|
| **Диагност** | Анализ ситуации, поиск узких мест | В начале цикла |
| **Стратег** | Генерация 2–3 стратегий + рекомендация | После Диагноста |
| **Декомпозер** | Разбивка выбранной стратегии на задачи | После выбора тренера |
| **Монитор** | Оценка прогресса стратегии | Периодически, параллельно |

---

## 4. Диагност

### 4.1. Задача

Проанализировать текущее состояние тренера и выявить **узкие места**: что работает, что не работает, почему, что можно улучшить.

### 4.2. Вход

| Данные | Откуда | Зачем |
|---|---|---|
| **Профиль тренера** | Анкета | Понять контекст: предложение, аудитория, ресурсы |
| **Метрики воронки** | CRM, логи | Увидеть цифры: касания, ответы, конверсии |
| **История задач** | Логи | Понять, что тренер делает, а что игнорирует |
| **Текущая стратегия** | БД | Оценить, работает ли она |
| **Карта компетенций** | Образовательный слой | Понять, чего тренер не умеет |

### 4.3. Что делает ИИ

- Сравнивает метрики с ожидаемыми для похожих тренеров
- Ищет паттерны: «много касаний, мало ответов» → проблема в сообщениях; «мало касаний» → проблема в действиях
- Формулирует гипотезы причин
- Отделяет «не работает» от «не делается»
- Оценивает, достаточно ли данных для выводов

### 4.4. Выход

Структурированный диагноз:

| Поле | Что содержит |
|---|---|
| `strengths` | Что работает: «Instagram даёт 80% заявок» |
| `bottlenecks` | Что не работает: «старая база не тронута» |
| `hypotheses` | Почему: «тренер не знает, как начать разговор» |
| `opportunities` | Что можно улучшить: «реактивация 50 лидов» |
| `skill_gaps` | Чего не умеет: «нет навыка работы с возражениями» |
| `data_quality` | Достаточно ли данных |

### 4.5. Валидация (код)

- Все поля заполнены
- Нет запрещённых формулировок (медицина, обещания)
- Если `data_quality` = «недостаточно» → уведомить тренера, запросить данные

### 4.6. Роль ИИ: высокая

Это интерпретация, а не правило. Код не может «понять», что проблема в сообщениях, а не в количестве касаний.

## 5. Стратег

### 5.1. Задача

На основе диагноза предложить **2–3 стратегии** с обоснованием, ожидаемым эффектом, требованиями к ресурсам и рисками. Дать рекомендацию.

### 5.2. Вход

| Данные | Откуда | Зачем |
|---|---|---|
| **Диагноз** | Диагност | Понять, что решать |
| **Профиль тренера** | Анкета | Понять, что реалистично |
| **RAG-методики** | База методик | Опираться на проверенные алгоритмы |
| **Few-shot примеры** | История | Учесть, что сработало у похожих |
| **Карта компетенций** | Образовательный слой | Не предлагать то, что тренер не осилит |

### 5.3. Что делает ИИ

- Подбирает релевантные методики из RAG по ключевым словам диагноза
- Комбинирует методики в стратегии
- Формулирует каждую стратегию: суть, обоснование, эффект, ресурсы, риски
- Сравнивает стратегии между собой
- Выбирает рекомендуемую и объясняет почему

### 5.4. Выход

2–3 стратегии + рекомендация:

| Поле | Что содержит |
|---|---|
| `id` | A, B, C |
| `name` | «Фокус на старую базу» |
| `description` | Суть стратегии |
| `rationale` | Почему подходит именно этому тренеру |
| `expected_effect` | Что изменится (без конкретных цифр) |
| `resource_requirements` | Что нужно от тренера |
| `risks` | Что может пойти не так |
| `methods_used` | Какие методики из RAG задействованы |
| `recommendation` | Какую рекомендуем и почему |

### 5.5. Валидация (код)

- Не менее 2 стратегий
- Все поля заполнены
- Нет запрещённых формулировок
- `methods_used` ссылаются на реальные методики из RAG
- Стратегии соответствуют ресурсам тренера

### 5.6. Роль ИИ: высокая

Это генерация вариантов с обоснованием. Код не может «придумать» стратегию.

## 6. Выбор тренера (Human-in-the-loop)

### 6.1. Задача

Тренер видит 2–3 стратегии и выбирает одну. Или просит перегенерировать.

### 6.2. Что показывается

| Элемент | Зачем |
|---|---|
| Название и суть | Понять, о чём стратегия |
| Обоснование | Понять, почему это подходит |
| Ожидаемый эффект | Понять, что изменится |
| Требования к ресурсам | Понять, что нужно делать |
| Риски | Понять, что может пойти не так |
| Рекомендация | Понять, что советует система |

### 6.3. Почему это важно

- **Governance:** финальное решение за человеком.
- **Вовлечённость:** тренер чувствует контроль.
- **Адаптация:** выбор тренера — сигнал для обучения.

### 6.4. Что логируется

- Какие стратегии показаны
- Какую выбрал тренер
- Выбрал ли рекомендованную
- Сколько времени думал

## 7. Декомпозер

### 7.1. Задача

Разбить выбранную стратегию на **конкретные задачи и вехи** с критериями успеха.

### 7.2. Вход

| Данные | Откуда | Зачем |
|---|---|---|
| **Выбранная стратегия** | Выбор тренера | Понять, что декомпозировать |
| **Профиль тренера** | Анкета | Понять ресурсы и ограничения |
| **Шаблоны задач** | RAG | Опираться на проверенные формулировки |
| **Карта компетенций** | Образовательный слой | Добавить обучающие шаги |

### 7.3. Что делает ИИ

- Разбивает стратегию на вехи (крупные этапы)
- Для каждой вехи — конкретные задачи
- Определяет частоту: разово, ежедневно, еженедельно
- Формулирует критерии успеха
- Добавляет обучающие шаги, если задача требует нового навыка

### 7.4. Выход

| Поле | Что содержит |
|---|---|
| `milestones` | Вехи с дедлайнами |
| `tasks` | Задачи: формулировка, тип, частота, привязка к лиду |
| `success_criteria` | Метрики, цели, дедлайны |
| `micro_learning` | Обучающие шаги (если нужны) |

### 7.5. Валидация (код)

- Задачи соответствуют типу стратегии
- Нет задач, противоречащих ограничениям тренера
- Критерии измеримы
- Максимум 10 задач на старте (чтобы не перегрузить)

### 7.6. Роль ИИ: высокая

Перевод абстракции в конкретику — это генерация.

---

## 8. Монитор

### 8.1. Задача

Периодически оценивать, **работает ли стратегия**, и рекомендовать: продолжить, скорректировать или сменить.

### 8.2. Вход

| Данные | Откуда | Зачем |
|---|---|---|
| **Стратегия** | БД | Понять, что оцениваем |
| **Критерии успеха** | Декомпозер | Понять, к чему стремились |
| **Метрики за период** | Логи | Понять, что произошло |
| **История выполнения** | Логи | Понять, делал ли тренер задачи |

### 8.3. Что делает ИИ

- Сравнивает метрики с критериями успеха
- Оценивает, достигнуты ли цели
- Если нет — ищет причины: «задачи не выполнялись» vs «выполнялись, но не сработало»
- Формулирует рекомендацию

### 8.4. Выход

| Поле | Что содержит |
|---|---|
| `status` | on_track / behind / failed / too_early |
| `explanation` | Почему такой статус |
| `what_works` | Что работает |
| `what_doesnt` | Что не работает |
| `recommendation` | continue / adjust / change_strategy |
| `adjustment_suggestions` | Что можно поправить |

### 8.5. Валидация (код)

- Если данных мало → принудительно `too_early`
- Если `recommendation` = `change_strategy` → триггер на новый цикл

### 8.6. Роль ИИ: умеренная

Оценка на основе данных + интерпретация причин.

## 10. Данные слоя

### 10.1. Что хранится

| Сущность | Что содержит | Срок |
|---|---|---|
| `strategies` | Все стратегии (активные + архив) | Постоянно |
| `strategy_runs` | Каждый запуск цикла | 1 год |
| `strategy_tasks` | Задачи из стратегий | Постоянно |
| `diagnoses` | Диагнозы | 1 год |
| `few_shot_examples` | Примеры для промптов | Постоянно |

### 10.2. Версионирование

Каждый промпт имеет версию. В `strategy_runs` пишется:
- `prompt_version` для каждого агента
- `model`
- `input_hash`
- `output_hash`
- `validation_result`

Это позволяет откатить промпт, сравнить версии, разобрать инцидент.

## 11. RAG-база методик

### 11.1. Что это

Векторная база алгоритмов продаж, шаблонов, кейсов, ограничений. Позволяет Стратегу опираться на **вашу методику**, а не на общие знания из интернета.

### 11.2. Структура

| Уровень | Что содержит | Пример |
|---|---|---|
| **Алгоритмы** | Крупные блоки | «Реактивация спящих лидов» |
| **Тактики** | Шаги алгоритма | «Сегментация базы» |
| **Шаблоны** | Готовые фразы | «Привет, {{name}}! Вспомнил о тебе...» |
| **Ограничения** | Что нельзя | «Не давить, если просили паузу» |

### 11.3. Как используется

- Стратег запрашивает методики по ключевым словам из диагноза
- RAG возвращает топ-5 релевантных
- Они подкладываются в промпт
- Модель генерирует стратегию, опираясь на них

### 11.4. Как обновляется

- Успешные кейсы → новые методики
- Провальные → пометка «не работает в такой ситуации»
- Обновление: вручную раз в месяц по агрегатам

---

## 12. Few-shot примеры

### 12.1. Что это

Примеры из прошлого опыта: «профиль → стратегия → результат». Подкладываются в промпт Стратега, чтобы он учитывал, что сработало, а что нет.

### 12.2. Формат

| Поле | Что содержит |
|---|---|
| `profile` | Профиль тренера |
| `diagnosis` | Диагноз |
| `strategy` | Выбранная стратегия |
| `result` | Результат |
| `conclusion` | Вывод |

### 12.3. Как используется

- При вызове Стратега достаются 3–5 релевантных примеров
- Подкладываются в промпт: «Вот похожие случаи. Учти их.»
- Модель генерирует стратегию с учётом опыта

### 12.4. Как обновляется

- После завершения каждой стратегии → новый пример
- Раз в месяц — ревизия: устаревшие удаляются

---

## 13. Валидация ответов ИИ

Каждый выход агента проверяется кодом.

### 13.1. Общие проверки

| Проверка | Что делаем |
|---|---|
| JSON соответствует схеме | Отбраковка, повтор 1 раз, затем fallback |
| Все поля заполнены | Отбраковка |
| Нет запрещённых формулировок | Отбраковка |
| Длина в пределах лимита | Обрезка или отбраковка |

### 13.2. Специфические проверки

| Агент | Проверка |
|---|---|
| **Диагност** | Гипотезы не противоречат данным |
| **Стратег** | `methods_used` из RAG; стратегии реалистичны |
| **Декомпозер** | Задачи не противоречат ограничениям; максимум 10 |
| **Монитор** | При малых данных → `too_early` |

---

## 14. Fallback

При любом сбое — система не остаётся без результата.

| Сбой | Fallback |
|---|---|
| Диагност упал | Уведомить, не запускать Стратега |
| Стратег упал | Повторить 1 раз, затем «продолжить текущую стратегию» |
| Декомпозер упал | Задачи не создаются, шаблонный набор |
| Монитор упал | Статус `too_early`, ручной пересмотр |
| Провайдер недоступен | Режим «без ИИ» до восстановления |

---

## 15. Governance

### 15.1. Ограничения (проверяются кодом)

- Не медицина, не питание, не юристы
- Не обещания конкретных цифр
- Не давление на лида
- Стратегии только из RAG-методик
- Задачи только из разрешённых типов

### 15.2. Human-in-the-loop

- Тренер утверждает стратегию
- Тренер может отклонить задачу
- Тренер может запросить пересмотр

### 15.3. Аудит

- Каждый цикл логируется
- Тренер может посмотреть, почему предложена стратегия
- При жалобе — полная трассировка

### 15.4. PII-минимизация

- Имена → макросы
- Телефоны, ники, каналы — не передаются в модель
- Санитайзинг текстовых полей

## 16. Влияние образовательного слоя

| Агент | Что меняется |
|---|---|
| **Диагност** | Оценивает не только «что не работает», но и «чего не умеет» |
| **Стратег** | Учитывает зону ближайшего развития |
| **Декомпозер** | Добавляет обучающие шаги к задачам |
| **Монитор** | Учитывает прогресс в навыках |

## 17. Влияние адаптации

| Что адаптируется | Как |
|---|---|
| Профиль | Подстановка в промпты всех агентов |
| Стиль | Влияет на формулировки |
| История | Влияет на выбор стратегий (few-shot) |
| Компетенции | Влияет на сложность задач |

## 18. Метрики слоя

| Метрика | Что показывает |
|---|---|
| Доля тренеров, выбравших рекомендованную стратегию | Качество рекомендаций |
| Доля стратегий, достигших критериев успеха | Эффективность |
| Среднее время до пересмотра | Стабильность |
| Доля задач из стратегии, выполненных | Реалистичность декомпозиции |
| Конверсия до/после стратегии | Влияние на бизнес |
| Доля fallback | Надёжность |

---

## 19. Экономика

| Параметр | Значение |
|---|---|
| Вызовов на цикл | ~4–6 (Диагност + Стратег + Декомпозер + Монитор) |
| Стоимость цикла | ~0,16–0,24 ₽ |
| Частота | Раз в 2–4 недели |
| Стоимость на тренера в месяц | ~0,16–0,48 ₽ |

---

## 20. Что это значит для реализации

### Минимальный MVP

1. Таблица `strategies` (профиль, диагноз, стратегии, выбранная)
2. RAG-база методик (5–10 алгоритмов)
3. Промпты: Диагност, Стратег, Декомпозер
4. UI выбора стратегии
5. Интеграция с операционным слоем (задачи из стратегии)
6. Логирование в `strategy_runs`

### Что можно отложить

- Монитор (запускать вручную)
- Few-shot примеры (если нет данных)
- Автоматические триггеры
- Скоринг стратегий

### Что нельзя откладывать

- Версионирование промптов
- Логирование вызовов
- Валидация ответов кодом
- Human-in-the-loop на выбор стратегии
- Fallback при сбое

## Итог

| Аспект | Решение |
|---|---|
| **Назначение** | Куда идём и почему |
| **Ритм** | Раз в 2–4 недели |
| **Агенты** | Диагност, Стратег, Декомпозер, Монитор |
| **Роль ИИ** | Высокая |
| **Ключевой принцип** | ИИ предлагает, тренер выбирает, код валидирует |
| **Вход** | Профиль, метрики, история, RAG, few-shot |
| **Выход** | Стратегия, задачи, критерии успеха |
| **Связь** | С операционным слоем (задачи), с образовательным (компетенции), с логированием (обучение) |

**Главная идея:** стратегический слой превращает разрозненные действия тренера в **осмысленное направление**. Он не просто ставит задачи, а объясняет, почему они важны, и помогает выбрать путь. Без него система остаётся исполнителем, а не партнёром.
