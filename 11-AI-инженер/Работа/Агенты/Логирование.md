# Логирование: полное описание

## 1. Назначение

**Логирование** — это не «журнал ради журнала», а **фундамент для обучения, аудита и отладки**. Без него стратегический слой не сможет учиться, а вы не сможете доказать, что система работает корректно.

**Задача:** собирать структурированные данные о каждом вызове ИИ, каждом решении, каждом действии тренера — чтобы:
- Понимать, что происходит в системе
- Находить и разбирать инциденты
- Оценивать качество работы агентов
- Замыкать цикл обучения
- Проходить аудит и обеспечивать governance

**Ритм:** постоянный. Логирование — сквозной компонент, который пронизывает все слои.

**Роль ИИ:** нет. Логирование и агрегация — это код.

## 3. Принципы

**1. Логирование — часть архитектуры, а не «добавим потом».**
Без структурированных логов система не сможет учиться.

**2. Структурированные логи, а не текстовые.**
Каждая запись — это структура с фиксированной схемой. Это позволяет автоматически агрегировать, фильтровать и строить метрики.

**3. PII-минимизация на входе.**
Если данные не нужны для работы — они не логируются. Если нужны — маскируются. Имена → макросы. Телефоны, ники, каналы — не логируются.

**4. Три горизонта хранения.**
- Тексты (промпты, ответы) — короткий срок (30 дней)
- Метаданные (модель, токены, результат) — длинный (1 год)
- Агрегаты (метрики) — постоянный

**5. Версионирование.**
Каждый промпт имеет версию. Это позволяет откатить, сравнить, разобрать инцидент.

**6. Логирование — не самоцель.**
Логи нужны для обработки: агрегации, обучения, аудита.

## 4. Что логируется

### 4.1. Каждый вызов ИИ (`ai_runs`)

Ядро системы логирования. Каждый вызов модели — одна запись.

| Поле | Назначение | Срок |
|---|---|---|
| `run_id` | Уникальный идентификатор | Постоянно |
| `timestamp` | Время вызова | Постоянно |
| `agent` | Какой агент вызван | Постоянно |
| `prompt_version` | Версия промпта | Постоянно |
| `model` | Модель | Постоянно |
| `input_hash` | Хеш входа | Постоянно |
| `input_tokens` | Токенов на входе | 1 год |
| `output_tokens` | Токенов на выходе | 1 год |
| `latency_ms` | Время ответа | 1 год |
| `cost_rub` | Стоимость вызова | 1 год |
| `validation_result` | Прошёл ли валидацию | 1 год |
| `fallback_used` | Был ли fallback | 1 год |
| `error_type` | Тип ошибки | 1 год |
| `input_text` | Текст входа (с макросами) | 30 дней |
| `output_text` | Текст ответа (с макросами) | 30 дней |

**Почему хеш, а не текст для `input_hash`:** хеш позволяет проверить, менялся ли вход, без хранения самого текста. Если нужно разобрать инцидент — текст есть в `input_text` в течение 30 дней.

**Агенты, которые логируются:**
- `diagnost` — Диагност
- `strategist` — Стратег
- `decomposer` — Декомпозер
- `monitor` — Монитор
- `executor` — Исполнитель
- `tool` — ИИ-инструменты

### 4.2. Запуски стратегического цикла (`strategy_runs`)

| Поле | Назначение |
|---|---|
| `run_id` | Идентификатор запуска |
| `trainer_id` | Тренер |
| `trigger` | Что запустило |
| `diagnosis_output` | Результат Диагноста |
| `strategies_generated` | Сгенерированные стратегии |
| `chosen_strategy_id` | Выбранная стратегия |
| `chosen_by` | Кто выбрал |
| `decomposition_output` | Результат Декомпозера |
| `total_cost_rub` | Стоимость всего цикла |
| `total_latency_ms` | Время всего цикла |

**Зачем:** полная трассировка стратегического цикла. Если тренер спросит «почему вы предложили именно это» — есть ответ.

### 4.3. Вызовы инструментов (`tool_runs`)

| Поле | Назначение |
|---|---|
| `run_id` | Идентификатор |
| `tool_name` | Название инструмента |
| `trainer_id` | Тренер |
| `lead_id` | Лид |
| `input_context` | Контекст (макросы) |
| `output_text` | Результат |
| `accepted_by_trainer` | Принял ли тренер |
| `edited_by_trainer` | Редактировал ли |
| `sent_at` | Отправлено ли |

**Зачем:** понимать, какие инструменты полезны, какие тренер игнорирует, где ИИ ошибается.

### 4.4. Ежедневные метрики (`metrics_daily`)

Агрегаты за день, не логи отдельных вызовов.

| Поле | Назначение |
|---|---|
| `trainer_id` | Тренер |
| `date` | Дата |
| `tasks_total` | Всего задач |
| `tasks_completed` | Выполнено |
| `tasks_postponed` | Отложено |
| `tasks_rejected` | Отклонено |
| `brief_ai_used` | Был ли ИИ в брифе |
| `brief_fallback_used` | Был ли fallback |
| `touches_made` | Касаний сделано |
| `responses_received` | Ответов получено |
| `bookings` | Записались |

**Зачем:** основа для обучения. По этим данным корректируются веса скоринга и оценивается прогресс стратегии.

### 4.5. Образовательные сигналы (`micro_learning`)

| Поле | Назначение |
|---|---|
| `trainer_id` | Тренер |
| `skill` | Навык |
| `micro_learning_shown` | Какая подсказка показана |
| `micro_learning_ignored` | Проигнорировал |
| `micro_learning_applied` | Применил |
| `skill_gap_detected` | Обнаружен разрыв |
| `skill_improved` | Навык улучшился |

**Зачем:** чтобы понимать, какие подсказки работают, а какие — нет. И чтобы видеть прогресс тренера.

## 5. Схема логирования: стандарт

Если вы хотите, чтобы логи были переносимыми и понятными для любых инструментов observability — используйте **стандартные атрибуты**.

### 5.1. Ключевые атрибуты

| Атрибут | Что означает |
|---|---|
| `operation_name` | Тип операции (`chat`, `invoke_agent`, `execute_tool`) |
| `request_model` | Запрошенная модель |
| `response_model` | Фактически ответившая модель |
| `usage_input_tokens` | Токенов на входе |
| `usage_output_tokens` | Токенов на выходе |
| `agent_name` | Имя агента |
| `conversation_id` | Идентификатор сессии |

### 5.2. Почему это важно

- **Переносимость:** логи можно отправить в любой backend без переписывания.
- **Стандартизация:** не нужно изобретать свою схему.
- **Мультиагентность:** если у вас несколько агентов, дерево вызовов строится автоматически.

**Практический совет:** начните с простого формата (одна строка — один вызов), но **используйте стандартные имена атрибутов**. Это дёшево сейчас и бесценно, когда вы захотите подключить дашборд.

## 6. Дальнейшая обработка логов

Логи — это сырьё. Ценность появляется при обработке.

### 6.1. Агрегация (ежедневно)

**Что агрегируется:**
- По тренеру: сколько задач выполнено, сколько отложено, конверсия
- По агенту: сколько вызовов, средняя латентность, доля fallback
- По инструменту: сколько раз использован, принят ли результат
- По стратегии: прогресс к критериям успеха

**Куда идёт:** в `metrics_daily` и в дашборд.

### 6.2. Оценка качества (периодически)

**Что оценивается:**
- Доля валидных ответов ИИ
- Доля fallback (если растёт — проблема с промптом или данными)
- Доля принятых инструментов (если тренер игнорирует — инструмент бесполезен)
- Достижение критериев успеха стратегии

### 6.3. Обучение (замыкание цикла)

Данные из логов питают **четыре уровня обучения**.

| Уровень | Что берём из логов | Как используем |
|---|---|---|
| **Веса скоринга** | `tasks_completed` / `postponed` / `rejected` | Корректировка весов факторов |
| **Few-shot примеры** | `strategy_runs` + результат | Добавление примеров в промпт Стратега |
| **RAG-база** | `tool_runs` + `accepted_by_trainer` | Обновление методик и шаблонов |
| **Карта компетенций** | `micro_learning` сигналы | Обновление уровней навыков |

**Пример:** если из логов видно, что задачи типа «напоминание» отклоняются в 80% случаев — вес этого типа снижается. Если стратегия «старая база» достигает успеха — кейс добавляется в RAG.

### 6.4. Аудит и безопасность

**Что проверяется:**
- Наличие запрещённых формулировок в ответах ИИ
- Попытки injection (паттерны типа «ignore previous instructions»)
- Утечки PII (если маскирование не сработало)
- Аномалии (всплеск ошибок, рост стоимости)

**Автоматизация:** проверка трейсов на безопасность, возврат сигнала при критических находках.

## 7. Хранение

### 7.1. Горизонты

| Тип данных | Срок | Почему |
|---|---|---|
| Тексты (промпты, ответы) | 30 дней | Достаточно для разбора инцидента, минимизирует PII-риски |
| Метаданные (модель, токены, стоимость) | 1 год | Для аналитики и обучения |
| Агрегаты (метрики) | Постоянно | Для долгосрочного анализа |
| Версии промптов | Постоянно | Для отката и сравнения |

### 7.2. Версионирование промптов

Каждый промпт имеет версию. В `ai_runs` пишется:
- `prompt_version`
- `model`
- `input_hash`
- `output_hash`
- `validation_result`

Это позволяет:
- Откатить промпт, если качество упало
- Сравнить версии на A/B
- Разобрать инцидент

## 8. Governance

### 8.1. PII-минимизация

- Имена → макросы
- Телефоны, ники, каналы — не логируются
- Тексты хранятся 30 дней, затем удаляются
- Санитайзинг перед логированием

### 8.2. Аудит

- Каждый вызов логируется
- Тренер может посмотреть, почему задача в брифе
- При жалобе — полная трассировка

### 8.3. Лимиты

- 6 вызовов ИИ на тренера в сутки
- ≤ 0,22 ₽/сутки
- Логирование каждого вызова

| Доля fallback | Надёжность |

## 11. Что это значит для реализации

### Минимальный MVP

1. Таблица `ai_runs` с полями: `run_id`, `agent`, `prompt_version`, `input_hash`, `input_tokens`, `output_tokens`, `latency_ms`, `validation_result`, `fallback_used`, `error_type`. Тексты — опционально, с ограничением срока.
2. Таблица `metrics_daily` с агрегатами по тренеру.
3. Таблица `strategy_runs` для стратегического цикла.
4. Таблица `tool_runs` для инструментов.
5. Простая агрегация (запросы) для дашборда.
6. Ручной анализ логов раз в неделю для корректировки промптов и весов.

### Что можно отложить

- Стандартные атрибуты для observability
- Автоматическую корректировку весов
- Интеграцию с внешними observability-платформами
- Таблицу `micro_learning`

### Что нельзя откладывать

- Логирование каждого вызова ИИ
- Версионирование промптов
- Хранение `validation_result` и `fallback_used`
- Агрегаты по тренеру
- PII-минимизация
