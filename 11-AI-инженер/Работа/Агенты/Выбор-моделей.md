В контексте вашей системы принципы выбора модели — это не «выбрать одну лучшую», а **распределить разные задачи между разными моделями** так, чтобы каждая задача решалась адекватной моделью по цене, скорости и качеству.

---

## 1. Принципы выбора модели

### 1.1. Разделение по сложности задачи

Модели различаются по способности к рассуждению. Малые модели хороши для маршрутизации, классификации, извлечения ключевых слов. Средние — для следования инструкциям, суммаризации, структурированного вывода. Большие — для многошагового рассуждения, глубокого анализа, работы с богатым контекстом .

В вашей системе это означает:
- **Простые задачи** (проверка JSON по схеме, выбор из короткого списка) — малая модель.
- **Средние** (генерация «зачем», анализ ответа лида) — средняя модель.
- **Сложные** (Диагност, Стратег, Декомпозер) — большая модель.

### 1.2. Баланс точности, задержки и стоимости

Три фактора всегда в конфликте. Высокая точность требует большей модели, большая модель — медленнее и дороже. Низкая задержка требует малой модели, малая модель — риск галлюцинаций .

**Практическое правило:** начинайте с сильной модели, чтобы установить базовый уровень качества. Затем тестируйте более лёгкие модели для оптимизации стоимости, пока качество остаётся приемлемым .

### 1.3. Осведомлённость об инструментах

Если агент вызывает инструменты, модель должна поддерживать структурированный вывод (JSON, вызов функций). Не все модели одинаково хорошо справляются с этим. Маршрутизатор может учитывать определения инструментов при выборе модели .

### 1.4. Бюджет задержки на тип запроса

Разные типы запросов имеют разные допуски по времени. Интерактивный чат должен отвечать за секунды. Фоновая обработка может занять минуты. Оценка может длиться часы .

В вашей системе:
- **Утренний бриф** — жёсткий дедлайн (07:00), задержка критична.
- **Стратегический цикл** — запускается редко, задержка не критична.
- **Инструменты** — интерактивны, задержка важна.

### 1.5. Каскадная стратегия

Вместо одной модели для всего — каскад. Сначала дешёвая модель. Если результат не проходит контроль качества — эскалация к дорогой .

Исследования показывают сокращение затрат на 40–85% при 70–80% запросов, обрабатываемых дешёвой моделью .

## 2. Механизмы выбора

### 2.1. Маршрутизация по запросу

Вместо выбора модели «на этапе проектирования» — выбор на каждый запрос. Одна беседа может использовать три разные модели за пять ходов в зависимости от того, что требуется на каждом шаге .

**Уровни сложности:**
- **Низкая** — фактические вопросы, приветствия, простые уточнения → быстрая дешёвая модель.
- **Средняя** — оркестрация инструментов (вызов функции, передача аргументов, форматирование) → производительная модель среднего уровня.
- **Высокая** — синтез, многошаговое рассуждение, сложная генерация → передовая модель .

### 2.2. Каскад с контролем качества

Запрос идёт сначала к дешёвой модели. Затем результат проверяется:
- **Порог уверенности:** если модель выдаёт оценку уверенности ниже порога — эскалация .
- **Семантическая валидация:** проверка структуры или обязательных полей .
- **Классификатор:** обученный на исторических данных, предсказывает сложность до генерации .

### 2.3. Маршрутизатор как отдельная модель

Обученный маршрутизатор (не промпт, а обученная модель) может превосходить большие LLM в качестве выбора агента при доле их задержки и стоимости. Модель на 0.6B параметров, обученная прогрессивно, показала задержку 120ms против 683ms у Nova Lite и 2457ms у Haiku .

**Ключевой вывод:** качество выбора агента определяется сигналом обучения, а не размером модели .

### 2.4. Fallback при отказе

Если основная модель недоступна или возвращает ошибку — переход к запасной. Запасная модель может быть из другого региона или другого провайдера .

**Практическое руководство:**
- Основная модель: 2–3 попытки.
- Запасная: 1–2 попытки.
- Последняя: 0–1 попытка .

### 2.5. Разделение «советник — исполнитель»

Инвертированная топология: малая модель управляет процессом (вызывает инструменты, итерирует, форматирует вывод), большая модель только советует (отвечает на запросы исполнителя, даёт руководство). Большие токены тратятся только на低频, высокоинтеллектуальные шаги .

## 3. Применение к вашей системе

### 3.1. Распределение по агентам

| Агент | Тип задачи | Рекомендуемая модель |
|---|---|---|
| **Диагност** | Многошаговое рассуждение, анализ | Большая |
| **Стратег** | Синтез, генерация вариантов | Большая |
| **Декомпозер** | Структурированный вывод, планирование | Средняя–большая |
| **Монитор** | Оценка по критериям | Средняя |
| **Исполнитель** | Выбор из списка, генерация «зачем» | Малая–средняя |
| **Инструменты** | Генерация текста, анализ | Малая–средняя |
| **Маршрутизация** | Классификация, выбор | Малая |

### 3.2. Маршрутизация внутри операционного слоя

Утренний бриф — критичный по задержке. Каскад:
1. **Дешёвая модель** пытается выбрать 1–3 задачи из топ-N и написать «зачем».
2. **Контроль качества:** валидация JSON, проверка задач из списка, проверка длины.
3. **Если не прошло** — эскалация к средней модели.
4. **Если и она не прошла** — fallback «без ИИ».

Это даёт экономию при сохранении надёжности.

### 3.3. Fallback-цепочка

```
Основная: gpt-4o-mini (через Caila)
  ↓ (сбой или невалидный ответ)
Запасная: другая модель того же класса (если доступна)
  ↓ (сбой)
Fallback: правила без ИИ
```

**Важно:** запасная модель должна быть из другого региона или провайдера, чтобы отказ одного не блокировал систему .

## 4. Что это значит для реализации

### 4.1. Минимальный MVP

1. **Одна модель** для всех агентов (gpt-4o-mini) — как сейчас.
2. **Fallback на правила** при сбое — как сейчас.
3. **Логирование** выбора и результата — для будущей оптимизации.

### 4.2. Что можно добавить

1. **Разделение по агентам:** малая для Исполнителя, средняя для Декомпозера, большая для Стратега.
2. **Каскад** для операционного слоя: малая → средняя → fallback.
3. **Маршрутизатор** для выбора модели на каждый запрос.

### 4.3. Что нельзя откладывать

- **Валидация выхода** — независимо от модели.
- **Fallback** — независимо от модели.
- **Логирование** — версия модели, задержка, стоимость, результат валидации.

## 5. Связь с другими компонентами

| Компонент | Что даёт |
|---|---|
| **Оркестратор** | Выбирает модель для каждого вызова по правилам |
| **Логирование** | Фиксирует модель, задержку, стоимость, валидацию |
| **Скоринг** | Не зависит от модели (код) |
| **Обучение** | Анализирует, какая модель даёт лучший результат при меньшей стоимости |

## Итог

| Принцип | Решение |
|---|---|
| **Не одна модель для всего** | Распределение по сложности задачи |
| **Баланс точности, задержки, стоимости** | Начинать с сильной, оптимизировать к слабой |
| **Осведомлённость об инструментах** | Модель должна поддерживать структурированный вывод |
| **Бюджет задержки** | Разный для брифа, стратегии, инструментов |
| **Каскад** | Дешёвая → контроль → дорогая |
| **Fallback** | Обязателен при сбое |
| **Маршрутизация** | Может быть обученной моделью, а не промптом |

**Главная идея:** выбор модели — это не «какая лучше», а **распределение задач по адекватным моделям**. Для вашей системы это означает: малая модель для рутины, средняя для структурированного вывода, большая для рассуждений — с обязательным fallback на каждом уровне.
