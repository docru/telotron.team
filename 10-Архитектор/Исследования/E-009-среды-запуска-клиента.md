### 1.5.1 Обновление клиента — **обязательно** (Mini App; тот же контракт желателен и для PWA)

Нет SW → нет нашего мягкого обновления по кэшу SW. Риски HTTP-кэша WebView (особенно **HTML/entry**): голый `reload()` может снова взять старый документ.

«Мягкая» здесь = **отложенный полный reload**, не подмена одного файла на лету (новый `build` = новый граф чанков).

**База:**

1. `Cache-Control` на HTML/entry: `no-store` или очень короткий max-age.
2. Проверка `/version.json` с `{ cache: 'no-store' }` (старт / `visibilitychange` / `online`).
3. Хэши чанков Vite — как есть; при reload при необходимости `?b=<build>` на URL документа.

**Политика момента reload** — поле в `/version.json`:

```json
{ "build": 42, "update": "defer" }
{ "build": 43, "update": "force" }
```

| `update` | Поведение |
|----------|-----------|
| **`defer`** (дефолт, если поля нет — тоже defer) | Запомнить pending. **Не** reload mid-screen. Сработать при: смене раздела (router), уходе с busy-экрана, возврате в приложение. Опционально тихий индикатор. |
| **`force`** | Ломающий релиз (API/auth). Reload ASAP; если `busy` (упражнение, flush outbox, грязная форма) — дождаться **safe-point**, затем reload. Не откладывать бесконечно. |

Клиент: флаг `pendingUpdate` + mode. Экраны только сообщают `busy` / safe-point — без знания version. Сервер выставляет `force` только когда старый клиент нельзя оставлять.

Без контура возможен залипший клиент против нового API. Must-have в ADR-008.

### 1.5.2 Host «Назад» (BackButton) — политика UX

В матрице это **возможность хоста** (системная «назад» в chrome Mini App), не наша кнопка в PWA.

**Политика:**

1. **Скрывать** host BackButton везде, где SDK умеет (`hide` / аналоги Bridge).
2. Где скрыть нельзя или сработал system/hardware back — **обработать**: переход на **главную** зоны (корень кабинета), не stack-back по history и не no-op.
3. Если уже на главной — **закрыть** Mini App (чтобы не ловить пользователя на повторных «назад»).

Capability `hasHostBackButton` в контракте остаётся; реализация пилота = hide-first + fallback → home / close.

### 1.5.3 Наложение PWA и Mini App в одном браузере — **риск, must-have митигации**

Сценарий: пользователь открывал зону как **PWA/top-level**, затем в том же браузере — ту же зону как **Mini App в iframe** (VK и т.п.) на **том же origin**.

| Что | Риск |
|-----|------|
| Service Worker | Высокий: SW scope `/` может контролировать iframe → чужой shell/cache/update |
| Cache Storage | Общий precache с PWA |
| localStorage / IDB / sessionStorage | Общие hints, outbox, passkey hint между режимами |
| Cookie | Partition/SameSite — непредсказуемо; путаница cookie-сессии и launchToken |
| Манифест | Слабее (из iframe редко ставят PWA), но `<link rel=manifest>` в host-entry лишний |

**Митигации (обязательны в адаптере / bootstrap этапа 7):**

1. Детект host-среды → **не регистрировать SW**; по возможности `unregister` для этой загрузки; без install nudge.
2. Host entry/layout **без** manifest и без SW-скрипта PWA (отдельный shell или условный layout).
3. **Namespace storage** по runtime (`pwa` vs `vk` / …) или отдельная IDB — не делить outbox/auth hints между режимами.
4. Auth строго по `authMode` среды: в iframe не опираться на «оставшиеся» cookie от top-level PWA.
5. Опционально позже: отдельный path/origin под Mini App для жёсткой изоляции.

Манифест из кэша — не главный страх; **SW + storage + смешанный auth** — да.

## 1.8 Зона welcome-clients (E-008 / ADR-007)

Третья **зона продукта** на своём host (`welcome-clients.*`): публичные `/callback/{nick}`, `/quiz/{nick}` → CRM. Сейчас в основном **Blade**, без кабинетной сессии (канон: без auth браузера).

| Тема | Pro / Client | welcome-clients |
|------|--------------|-----------------|
| Нужен ли RuntimeAdapter в Mini App | да (кабинет) | **да** (host chrome: Bridge init, Back, update/HTML cache) |
| Auth / Passkey / cookie-сессия кабинета | да (PWA) / launchToken (host) | **нет** как вход в кабинет; формы публичные |
| Launch verify | обязателен для сессии User | **опционально**: атрибуция `vk_user_id` / source в заявке CRM — отдельное PO; не блокер открытия формы |
| SW / offline / install | PWA-канон | обычно **нет** (лендинг-формы) |
| Главная для Back-fallback | корень кабинета зоны | корень сценария (например `/callback/{nick}` или `/quiz/{nick}`) / close |

**Вывод:** тот же контракт **среды** (адаптеры PWA/VK/…); другой профиль **зоны** (`authMode: none` или `optionalLaunch` + без Passkey/SW). Не строить отдельный «четвёртый продукт», но **заложить zone id `welcome-clients`** в bootstrap/capabilities с первого контракта, иначе потом выламывать Pro/Client-only допущения.

Пилот порядка (рекомендация): контракт общий → `PwaAdapter` → VK на одной зоне; **welcome-clients в VK** часто выгодный ранний срез для I-001 (лидген), параллельно или сразу после кабинетного пилота — уточнит PO на этапе 7.

# Этап 4 · Auth для пилота

## 4.1 Модель

| Среда | Вход | Сессия API |
|-------|------|------------|
| PWA | OTP / Passkey / OAuth как сейчас | Sanctum **cookie** + CSRF |
| VK (пилот) | Verify launch `sign` на бэке → связать/создать User зоны | Наша сессия: **Bearer token** (или эквивалент без cookie) в `Authorization`; клиент кладёт через `applyAuthToRequest` |
| MAX / TG (позже) | Verify `initData` → link User | Тот же `launchToken` path |
| OK | Как VK Mini Apps | Как VK |
| welcome-clients (любая среда) | Публичные формы; кабинетной сессии нет | `none` / опц. `optionalLaunch` для атрибуции (§1.8) |

## 4.2 Правила Identity

1. Launch params / initData **никогда** не доверять с клиента без HMAC/sign на сервере.
2. После verify — **наша** сессия (TTL, revoke), не «вечный» проброс launch на каждый запрос (допустимо short-lived re-verify как доп. слой, не вместо сессии).
3. Связка `vk_user_id` / `max_user_id` / `tg_user_id` ↔ User зоны — таблица identity links (детали в реализации / ADR Identity при необходимости).
4. OTP-боты MAX/TG **остаются** каналом доставки кода в PWA; не заменяют Mini App login.
5. Passkey/WebAuthn в Mini App **не используем** (`hasPasskey: false`); вход = Bridge + verify launch (+ при необходимости подтверждение телефона продукта — отдельное PO-решение при реализации). В PWA Passkey остаётся.

## 4.3 Транспорт

- Расширить шов `http-config` / `api-client`: адаптер подставляет credentials **или** `Authorization`.
- Для `launchToken`: CSRF cookie **не** требуется (stateless API token middleware) — отдельный guard path рядом с Sanctum SPA, не ломая PWA.

## 4.4 Риски

| Риск | Митигация |
|------|-----------|
| Replay launch | TTL `vk_ts` / `auth_date`; one-time exchange на session token |
| Утечка token в IDB | HttpOnly предпочтительнее cookie, но в iframe cookie мёртв → memory + sessionStorage с осторожностью; короткий TTL + refresh |
| Смешение зон | Token несёт zone; host/app_id проверять |
| PWA∩iframe same origin | §1.5.3: no SW в host, namespace storage, не смешивать cookie и launchToken |

# Этап 5 · Пилот

## 5.1 Выбор

| Вариант | Вердикт |
|---------|---------|
| **VK Mini Apps** | **Пилот** (уже в скоупе эпика S1) |
| OK | Тот же стек Bridge; после VK почти бесплатно |
| MAX | Реалистичный второй кандидат (есть официальный Mini App); после VK |
| Telegram | Аналогично MAX по auth; после VK |
| Только контракт без VK | Отклонено скоупом |

## 5.2 Срез UX пилота (минимальный)

**В пилоте VK:**

- Один zone-срез на выбор реализации (рекомендация research: начать с **Client** — меньше Pro-специфики Passkey/install; либо Pro, если бизнес-приоритет тренера в VK — уточнит PO при старте этапа 7).
- Bootstrap: Bridge init → передача launch → exchange token → hydrate session.
- Host BackButton: **hide-first**; если не скрылась / system back → переход на **главную** зоны; на главной → close Mini App (§1.5.2).
- Theme от хоста — опционально.
- **Без:** SW, install nudge, Passkey/WebAuthn, полного offline MVP.
- **С:** контур обновления (§1.5.1) — `version.json` + `update: defer|force` + busy/safe-point + no-store HTML.
- Экраны: тот же Vue router/ядро; скрыть UI под `hasInstallPrompt` / `hasPasskey`.

**Вне пилота:** публикация в каталог VK как отдельный чеклист продукта; deep links / bot notify — не блокер контракта.

## 5.3 Критерии успеха пилота

1. Пользователь открывает мини-приложение в VK → видит кабинет зоны без ручного OTP (или с минимальным link-flow, если PO потребует).
2. API-мутации работают без Sanctum cookie.
3. Ядро не содержит `bridge.send`.
4. PWA регрессии нет (PwaAdapter = прежнее поведение).
5. Смена `build` подхватывается: `defer` не рвёт mid-screen; `force` — после safe-point; HTML не залипает в кэше.
6. Host-сессия на том же origin, что PWA: без регистрации SW / без общего storage с PWA-режимом (§1.5.3).
