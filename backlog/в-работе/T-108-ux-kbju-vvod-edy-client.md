## 4) Фаза A · Архитектор

### Задачи

1. **Модель данных** КБЖУ у блюда (и агрегата слота — в API или на клиенте): ккал, Б, Ж, У; null / частичные значения; источник (`manual` \| `product` \| `barcode` \| …).
2. **API дневника:** create/patch dish с КБЖУ; ответ слота с суммой (или полями для суммирования на клиенте).
3. **Autocomplete / barcode:** поиск **только** в локальной **РФ**-базе (дамп OFF). Live API OFF **не** вызываем (A12/A15). Miss → «не найдено» / ручной ввод. Блюдо — отдельный create/patch.
4. ~~клиент → live OFF~~ — **снято** (пересмотр PO после проблем с `search.pl`).
5. **Пересчёт порции:** канон `на_100г × (граммы / 100)` (или эквивалент для мл/шт — описать).
6. **Decode фото штрихкода:** **клиент** (A3); на бэк только EAN.
7. **Offline / outbox:** блюдо без lookup можно (A4–A5).
8. **Импорт дампа РФ** + cron + атрибуция ODbL — follow-up после B (код B ещё ходил в live OFF).
9. Техдок: схема / api-http — обновить под «без live OFF».

### Порядок взаимодействия сисадмин ↔ разработчик (чтобы не мешать)

Можно и нужно идти **параллельно**. Общий блокер один: согласованный путь к файлу дампа и один совместный прогон полного импорта на стенде.

```text
День 0 (коротко, вместе, 15–30 мин)
  · Зафиксировать путь дампа (канон): например /var/lib/telotron/off/current.tsv.gz
  · Зафиксировать формат: TSV OFF (tab; опц. .gz); env NUTRITION_OFF_DUMP_PATH
  · Staging: кто имеет права читать этот путь от пользователя приложения

Параллельно
  Сисадмин                          Разработчик
  ─────────                          ───────────
  диск, каталог, права               fixture 10–50 товаров РФ
  скрипт скачивания дампа            nutrition:import-off-dump на fixture
  cron + ротация                     убрать live OFF с клиента
  мониторинг / ops-инструкция        suggest/by-barcode только БД
                                     UI «не найдено», тесты, техдок

Стык 1 (staging) — когда первый дамп скачан
  · Сисадмин: файл лежит по канон-пути, права ок
  · Разработчик: полный import --ru-only на staging
  · Вместе: smoke suggest + barcode; место на диске / время импорта

Стык 2 (prod) — после зелёного staging
  · Сисадмин: тот же процесс скачивания/cron на prod
  · Разработчик: один импорт (или из CI/деплоя по договорённости)
  · Вместе: короткий smoke; не запускать полный импорт на prod без предупреждения

После C
  · Сисадмин владеет свежестью дампа (cron)
  · Разработчик владеет командой импорта и поиском в приложении
  · Повторный полный импорт / смена формата — согласовать заранее
```

**Правила**

1. Разработчик **не ждёт** полный дамп, чтобы писать код — только fixture.  
2. Сисадмин **не** правит схему БД и не вызывает artisan без согласованной команды.  
3. Live OFF можно снять с клиента **до** полного каталога (временно чаще «не найдено»).  
4. Путь к дампу и формат меняются только по договорённости обеих ролей (+ запись в техдок/ops).  
5. Полный импорт на prod — только после стыка 1 и с окном (нагрузка на диск/CPU).
