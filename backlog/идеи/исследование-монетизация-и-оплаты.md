## Зачем этот файл

Схема монетизации **принята и реализована** (абонплата тренера, Лайт / Профи / Макс, счёт в Ед., ЮKassa).  
Параллельно нужно **глубже исследовать** альтернативы и соседние модели (конкуренты, WTP, способы оплаты), чтобы:

- не застрять в единственном narrative без проверки рынком;
- понимать, **чем бить** Режим / ФитнесПлан / ROKKFIT в КП;
- иметь backlog гипотез для **после-пилота** (не смешивать с текущим scope Commerce);
- разбирать схемы на **оси** (§2) и видеть архитектурный след до DEC.

**Правило:** пока нет явного решения директора — **канон не меняем**. Сюда пишем гипотезы, сравнения, вопросы к юристу/буху/пилоту.

## 2) Таксономия: оси и архитектура

Не список «моделей конкурентов», а **набор независимых осей**. Любая схема (Telotron, Режим seats, ФитнесПлан, лидоген, revshare) = комбинация значений по осям. По каждой оси — **архитектурный след** (сущности, jobs, gating, юр.).

**Правило:** менять значение оси без DEC нельзя; checklist в конце §2.

Канон Partner для MVP: [partner-модуль-тз-mvp](../../../_telotron.ru/docs/Техдок/03-модули/partner-модуль-тз-mvp.md) (supersedes порог S / отдельный партнёрский счёт / закрытие 1-го числа).

### 2.1. `payer` — кто платит платформе

| Значение | Пример | Архитектура |
|----------|--------|-------------|
| Тренер (Pro) | Telotron, ФитнесПлан, Режим seats | `Commerce` на trainer; Client без checkout |
| Клиент (Client) | гипотеза подписки Client | биллинг-аккаунт у Client; две payer-модели |
| Оба | гибрид | два ledger / два договора |
| Третий (студия / org) | тариф студии | org account, роли, invoice B2B |

**Не путать** с тем, кто получает деньги клиента за сопровождение — это ось `client_money`.

### 2.2. `charge_object` — за что платят

| Значение | Пример | Архитектура |
|----------|--------|-------------|
| Доступ к софту (подписка) | Лайт / Профи / Макс | tariff + gating по capability |
| Seat / активный клиент | Режим 390×N | метрика «активный», recalc, anti-fraud |
| Квота слотов клиентов | ФитнесПлан 3/15/50 | quota + soft/hard limit в API |
| % / доля с платежа клиента | revshare | платежный split, payout, споры |
| Лид / заявка | каталог | lead entity, attribution, цена лида |
| Разовая услуга (SKU) | допы | catalog + one-shot invoices |

### 2.3. `price_drivers` — от чего зависит размер оплаты

Абстрактно:

```text
к_оплате = f(база) − скидки − partner_credit + fees
```

| Драйвер | Пример | Архитектура |
|---------|--------|-------------|
| Фикс тарифа | 5 000 Профи | `tariff.price`, пакет 30 × дневная ставка |
| Число сущностей (clients, seats) | seats / квоты | счётчики + snapshot биллинг-периода |
| Usage (SMS, storage…) | редко | meters + aggregation jobs |
| Оборот клиент→тренер | take rate | money flow **через** платформу |
| Trial / купоны | Ед., trial 30 д | ledger entries, expiry |
| **Partner commission** | % от topup приглашённых | событие topup → начисление предкам (см. §2.7) |

### 2.4. `billing_mechanics` — период и механика списания

| Механика | У нас / альтернатива | Архитектура |
|----------|----------------------|-------------|
| Prepaid ledger + daily debit | **канон Ед.** | balance, nightly job МСК, freeze→light |
| Calendar month invoice | классика SaaS | invoice, dunning, grace |
| Per-seat monthly | Режим | «активный на дату X» → invoice |
| Per-transaction fee | marketplace | fee на каждом payment |
| Recurring card | автопополнение | saved method, retry |

**Критично для Telotron:** ось времени Commerce (пакет ~30 дней / сутки МСК) и начисления Partner (на **каждый** успешный topup) — разные триггеры; не смешивать в одном job без явной модели.

### 2.5. `entitlement` — как режем free / paid

| Рычаг | У нас | Архитектура |
|-------|-------|-------------|
| Capability / модули | **основной** | `tariff-capabilities.php`, TariffGate |
| Quota (N клиентов) | нет на Лайте | counters + 403 |
| Trial then paid | 30 дн. как Профи | `trial_ends_at`, один раз на аккаунт |
| Feature flags по usage | — | meters |

### 2.6. `client_money` — поток клиент → тренер (отдельный контур)

| Режим | Статус | Архитектура |
|-------|--------|------------|
| Вне платформы | **канон** | только учёт статусов (A2) |
| Учёт без эквайринга | как ФитнесПлан | тарифы клиента, overdue UI |
| Эквайринг + payout / НПД | идея | marketplace ЮKassa, split, ФНС |
| Take rate | не план | всё выше + % платформы |

**Под-ось:** кто задаёт цену сопровождения клиента — тренер / платформа / студия.

**Важно:** не смешивать `client_money` с `payer=тренер` в одном ledger без ADR.

### 2.7. `partner` — партнёрка как отдельная ось

Не «фича тарифа», а **модификатор economics** поверх платежей тренера платформе. Канон MVP — **тренер → тренер**; client→client / лидоген — **другие ветки** (не смешивать в одном модуле без решения).

| Вопрос | Канон MVP (Partner ТЗ) | Архитектурный след |
|--------|------------------------|-------------------|
| Кого приглашают? | тренер→тренер | `invite_tokens` `specialist_referral`, graph атрибуций |
| Кто получает выгоду? | L1 / L2 / L3 (20% / 5% / 2,5%) | обход предков по `referral_attributions` |
| База начисления? | сумма **успешного topup** приглашённого (downstream) | hook на Commerce topup; Лайт без topup → база 0 |
| Форма выгоды? | Ед. на **тот же** `commerce_accounts.balance` (`partner_commission`) | **единый** balance; различие только в type проводки |
| Когда начисляется? | на каждый успешный topup | идемпотентность UK по source topup + beneficiary + level |
| Вывод? | заявка + резерв ≥ 30 × daily_rate | payout adapter (ручной / ЮKassa) |
| Влияние на gating? | модуль на всех тарифах | capability ≠ «оплата = 0» |

**Исторические / альтернативные варианты** (бизнес-черновики; **не** MVP-код):

| Вариант | Отличие | Архитектурный след |
|---------|---------|-------------------|
| Отдельный partner ledger + закрытие 1-го числа | другая ось времени | второй balance, monthly job |
| Порог S + скидка на абонплату | зачёт в daily debit | правила «свои/чужие» Ед., FIFO |
| Начисления компании с platform recruitment | другой beneficiary | admin attribution без Partner % |

**Ветки оси (не путать):**

| Ветка | Статус | Связь |
|-------|--------|-------|
| `partner.trainer_ref` | **канон** | Partner module |
| `partner.client_ref` | идея | реферал клиент→клиент |
| `partner.lead_fee` | идея | плата тренеру за лид из каталога |

Связь: [partner-модуль-тз-mvp](../../../_telotron.ru/docs/Техдок/03-модули/partner-модуль-тз-mvp.md) · [модуль-партнерка](../../../_telotron.ru/docs/Бизнес-требования/02-модули/partner/модуль-партнерка.md) · [клиентский-маркетплейс-и-лидоген](клиентский-маркетплейс-и-лидоген.md).

### 2.8. Дополнительные оси (коротко)

| Ось | Зачем | Архитектура |
|-----|-------|-------------|
| **Атрибуция** | кто «владеет» конверсией | токен, дерево, запрет перепривязки; UTM/lead owner |
| **Юр. статус** | чеки, НДС, НПД | договор, self-employed flags |
| **Метод оплаты** | карта / СБП / безнал | провайдер; **не** смена модели |
| **Billing account** | solo vs org/студия | org entity, роли |
| **Валюта выгоды партнёра** | Ед. / ₽ / % скидки | разные проводки |

### 2.9. Матрица «схема = сумма осей»

| Схема | payer | charge | price_drivers | entitlement | client_money | partner |
|-------|-------|--------|---------------|-------------|--------------|---------|
| **Telotron канон** | тренер | подписка | фикс тарифа; partner_commission ↑ balance | модули + trial | вне | trainer_ref → Ед. на topup |
| **ФитнесПлан** | тренер | подписка | фикс + **квота клиентов** | квота (ф-ции одинаковы) | учёт | ? |
| **Режим UI** | тренер | seat×активный | N активных дневников | ? | вне (100% тренеру) | нет в UI |
| **Лидоген** | тренер | лид | цена лида | Макс / SKU | вне | lead_fee (± client_ref) |
| **Revshare** | клиент→платформа | % оборота | оборот | — | **через нас** | сложный |

### 2.10. Checklist: смена оси → что трогать

| Если меняем… | Трогаем |
|--------------|---------|
| `payer` | Commerce account owner; Client checkout?; договоры; Filament |
| `charge_object` → seats / quota | counters, «активный», billing snapshot, API 403 |
| `charge_object` → take rate / % | `client_money` через нас; payout; юр. |
| `price_drivers` (формула цены) | tariff table, public page, Pro UI topup |
| `billing_mechanics` | jobs списания, grace/freeze, invoices |
| `entitlement` | `tariff-capabilities`, TariffGate, Pro UI hide |
| `client_money` | отдельный модуль; **не** ломать Commerce ledger без ADR |
| `partner` форма выгоды | Partner + Commerce transactions; вывод; оферта |
| `partner` ветка client_ref / lead_fee | новый модуль/SKU; attribution; не ломать trainer_ref |
| метод оплаты (СБП…) | только адаптер ЮKassa / UX |

## 3) Карта моделей (что исследовать)

Не «выбрать вместо канона», а **знать ландшафт**. (Сводка примеров; детальная таксономия — §2.)

### A. Кто платит платформе

| Модель | Пример | Суть | Плюс | Минус для нас |
|--------|--------|------|------|---------------|
| **A1. Абонплата тренера** | Telotron (канон), ФитнесПлан | Фикс/ступень за софт | Простой юр. контур; деньги клиента — у тренера | Порог WTP; «плачу, даже если мало клиентов» |
| **A2. Revshare / take rate** | Режим *(раньше на лендинге)* | Клиент платит через платформу → доля | 0 ₽ на входе | В UI Режим **нет**; юр. сложность |
| **A2b. Seat SaaS** | **Режим (факт UI)** | Тренер платит **за активного** (у них = дневник) | Дешёвый старт | Линейный рост счёта (~13 акт. ≈ 5k) |
| **A3. Платит клиент (подписка Client)** | гипотеза | Клиент платит за app / дневник | Другой payer | Ломает «клиент free»; нужна ценность без тренера |
| **A4. Гибрид** | A1 + опциональный A2/A3/A2b | Подписка + допы | Гибкость | Сложнее объяснить и считать |
| **A5. Лидоген** | каталог / маркетплейс | Тренер платит за лид | Не трогает оборот с клиентом | Нужен трафик и качество лидов |

### B. Как режем free / paid

| Рычаг | Пример | У нас |
|-------|--------|-------|
| **Лимит клиентов** | ФитнесПлан 3→15→50 | **Не используем** на Лайте (канон) |
| **Модули / глубина** | Telotron Лайт | **Основной** рычаг |
| **Триал → платное** | Telotron 30 дн. | Реализовано |
| **Freemium навсегда** | Лайт 0 | Да |
| **Комиссия с оборота** | — | Нет |
| **Seat × активный** | Режим 390 ₽ | Не используем (фикс / модули) |

### C. Способы оплаты платформе (тренер → мы)

| Способ | Статус у нас | Исследовать |
|--------|--------------|-------------|
| Карта РФ (ЮKassa) | **MVP** | — |
| СБП | после MVP | Когда включать; комиссия; UX |
| Счёт юрлица / безнал | после MVP | B2B-студии, ИП |
| Рекуррент / автопополнение | идея | [commerce-автопополнение](commerce-автопополнение-с-карты.md) |
| Год / квартал со скидкой | нет в каноне | WTP vs cashflow; «без скидок за длительную предоплату» сейчас |
| Иностранные карты / валюта | нет | Не приоритет РФ |

### D. Оплаты клиент → тренер (смежный контур)

| Вариант | Статус | Файл / заметка |
|---------|--------|----------------|
| Вне платформы (как привык) | **канон сейчас** | — |
| Учёт статусов / долгов без эквайринга | частично / A2 | как у ФитнесПлан |
| Приём через платформу + чек НПД | идея | [оплаты-клиент-тренер-ндп-чеки](оплаты-клиент-тренер-ндп-чеки.md) |
| Marketplace split | не план | лендинг Режим раньше намекал; в UI Режим — seats, не split |
| Seat SaaS (per active) | у Режим | **390 ₽ × ведущий дневник** — альтернатива фиксу; см. §4 |
