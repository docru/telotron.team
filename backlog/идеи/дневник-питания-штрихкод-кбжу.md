## Суть

Дополнить **существующий дневник питания Client** (`ClientNutritionDiaryPage`, `nutrition_meals`) возможностью **добавить продукт по штрихкоду** и автоматически посчитать **КБЖУ порции**. Отдельное приложение не нужно — расширение модуля **Nutrition** в зоне Client.

Канон схемы сейчас: [nutrition-питание-схема-данных-mvp](../../_telotron.ru/docs/Техдок/03-модули/nutrition-питание-схема-данных-mvp.md) — приёмы: текст + фото, без КБЖУ.

**Связанная идея:** приготовленная еда без штрихкода → [дневник-питания-ии-оценка-кбжу.md](дневник-питания-ии-оценка-кбжу.md) (ИИ по тексту, шаг 3 после штрихкода).

## Зачем / для кого

- **Клиент** — быстрый ввод фабричных продуктов без ручного подсчёта.
- **Тренер** — видит приёмы с цифрами в уже существующей ленте/календаре (`meal` в feed); отдельный экран на старте не обязателен.

## UX (канон идеи)

**Клиент** в «Дневник питания»:

1. «Добавить приём» → **«Сканировать штрихкод»** (или ввести EAN вручную).
2. Название и КБЖУ **на 100 г**.
3. Ввод **веса порции (г)** → итог: ккал, Б, Ж, У.
4. Сохранение в `nutrition_meals` (фото по желанию, не вместо штрихкода).
5. Продукт не найден → **«Ввести вручную»** (название + КБЖУ на порцию или на 100 г).

**Тренер:** без нового экрана в MVP идеи — расширение существующего отображения приёма; сводка «за день» — опционально, вторым шагом.

## Архитектура

```text
Client PWA (камера / ZXing)
    → GET /api/v1/nutrition/barcode/{ean}   [auth:sanctum, Client]
        → Laravel (Nutrition)
            → кэш в БД (nutrition_products)
            → при промахе: Open Food Facts API
            → нормализованный JSON
    → UI: порция в граммах → расчёт
    → POST/PATCH nutrition_meals (как сейчас + поля КБЖУ)
```

**Почему через бэкенд, а не напрямую из браузера:** кэш, единый формат, лимиты, логирование, проще описать внешний запрос в политике ПДн.

**Внешний источник на старте:** [Open Food Facts](https://world.openfoodfacts.org) — бесплатно, без ключа, EAN-13, частичное покрытие РФ. Платные API (FatSecret, Chomp) — не нужны на пилоте.

**Сканер:** `html5-qrcode` или `@zxing/browser` в PWA; fallback — ручной ввод 13 цифр.

## Данные (черновик)

Расширить `nutrition_meals` (один продукт на приём в MVP):

| Поле | Назначение |
|------|------------|
| `barcode` | EAN-13, nullable |
| `product_name` | из API или ручной ввод |
| `portion_grams` | вес порции |
| `kcal`, `protein_g`, `fat_g`, `carbs_g` | **итог на порцию** (уже посчитанные) |
| `kbju_source` | `open_food_facts` \| `cache` \| `manual` |

Таблица **`nutrition_products`** (barcode PK, нутриенты на 100 г, `fetched_at`) — кэш и ручные дополнения при 404 от OFF.

Текст приёма и фото **остаются** — штрихкод дополняет текущий UX.

Расчёт: `итог = значение_100g × (граммы / 100)`.

## Поставка (предлагаемая)

| Шаг | Содержание |
|-----|------------|
| **1** | Ручной КБЖУ к приёму (без камеры) + поля в API/БД |
| **2** | Сканер + прокси OFF + кэш + fallback «не найден» |

Оценка шага 2: **~24–32 ч** (API, кэш, Client UI сканера, расчёт порции, тесты iOS/Android, атрибуция OFF).

## Ограничения MVP идеи

- Только **упакованные товары** со штрихкодом; домашняя еда — текст/фото или ручной КБЖУ.
- **Один продукт** на приём (составной обед — позже, `meal_items`).
- **Нет** целей тренера «съешь N ккал» и аналитики — только фиксация факта.
- **Нет** отдельного каталога продуктов в Pro.

## Юридическое и тариф

- Дневник уже под **согласием на мед. данные** — КБЖУ в том же in-app контуре.
- В политику: передача **штрихкода** на Open Food Facts при lookup.
- Атрибуция OFF в разделе «О данных».
- Тариф: **L-11** (глубина дневника); при необходимости лимит сканов на Лайте ([T-078](../бэклог/T-078-идеи-ограничения-тарифа-профи.md) — сборник идей, не scope).

## Гипотеза

Если клиент сканирует штрихкод вместо ручного ввода в мессенджер/сторонние калькуляторы, выше полнота дневника и ценность для тренера; проверка — доля приёмов с заполненным КБЖУ и успешность lookup на iOS/Android.
