## Суть

Альтернатива / дополнение к фикс-абонплате:

1. Тренер **сам** формирует цены и тарифы для клиентов.
2. Платформа берёт **комиссию с оборота** (клиент→тренер), ориентир **~10%** с транзакции.
3. **Отдельная** оплата за доп. функции / товары — с клиента и/или с тренера.
4. Тренер **сразу** получает деньги на счёт (после платежа).
5. **Партнёр** — расчёт / выплата **в конце месяца**.

Гипотеза автора: так **проще понять тренеру** и **проще технически**, чем сложный prepaid ledger + daily debit + отдельный контур учёта; плюс появляется учёт оплат и база для **скидочной программы**. Минус — **сложнее юридически**.

---

## Зачем / для кого

- Тренер: «плачу с оборота, как привык думать о бизнесе»; свои тарифы; деньги сразу.
- Платформа: выручка растёт с активностью; стимул помогать тренеру зарабатывать.
- Продукт: учёт оплат + скидки удержания ([УТП · столп удержание / автоматизация](утп-и-картина-развития-продукта.md)).

Связь с конкурентами: narrative ближе к **Режим** (доля с клиента) / marketplace, чем к ФитнесПлан (фикс + квота). Сверка TCO — в исследовании монетизации.

---

## Элементы схемы (черновик)

| Элемент | Предложение | Ось таксономии (§2) |
|---------|-------------|-------------------|
| Тарифы клиента | Тренер создаёт сам (как у ФитнесПлан: период / тренировки / разовая) | `client_money` + кто задаёт цену = **тренер** |
| Комиссия платформы | **~10%** с транзакции клиент→тренер | `charge_object` = % оборота; `payer` косвенно клиент |
| Доп. функции / товары | Отдельный прайс: платит клиент и/или тренер | SKU / гибрид `payer` |
| Выплата тренеру | **Сразу** на счёт (после успешного платежа) | payout / split ЮKassa |
| Партнёрка | Закрытие / выплата **в конце месяца** | `partner` — другая ось времени, чем payout тренеру |
| Скидки клиентам | На базе учёта оплат в продукте | удержание |

## Плюсы (по директору)

1. Проще **объяснить** тренеру («% с того, что прошло через систему»).
2. Проще **техмодель** относительно связки «Ед. + daily + отдельный A2-учёт без денег» — *гипотеза, проверить vs текущий Commerce*.
3. Естественный **учёт оплат** и фундамент **скидочной программы**.
4. Деньги тренеру **сразу** — меньше кассового трения.

## Минусы / риски

1. **Юридически сложнее**: эквайринг, split/marketplace, чеки, НПД, агентский договор, 54-ФЗ.
2. Конфликт с привычкой «СБП на свою карту» (барьер adoption — как у revshare).
3. При **малой базе** клиентов тренер может платить платформе **меньше**, чем фикс 5k — или **0**, если нет оборота через нас (риск MRR).
4. Партнёрка «в конце месяца» vs «сразу тренеру» — два контура выплат; нужна ясная модель (см. Partner MVP сейчас = commission на topup абонплаты).
5. Ломает / дополняет канон E-001 — нужен **DEC**, не тихий рефакторинг.

---

## Гипотеза

Если перевести монетизацию на **~10% с клиентских платежей через платформу** + тарифы тренера + мгновенный payout + partner EOM, то:

- выше готовность стартовать (нет «плачу 5k при 3 клиентах»);
- проще продать учёт и скидки;
- при росте оборота выручка платформы масштабируется.

Проверка: юр. заключение; TCO при 5/15/30 клиентах × средний чек; пилотный опрос «готовы ли пустить оплату через нас за 10%».
