## Суть

**Проблема:** автотестов уже много (PHPUnit, Vitest, E2E), их нужно **делать больше**, но **полный прогон** (`test:ts` + `php artisan test` + `test:e2e`) занимает **слишком много времени** — агент и разработчик часто «залипают» на полном комплекте или пропускают проверки.

**Направление 1 — система запусков:** явные **уровни** прогона (smoke → адресный → полный) с правилами «когда что гонять», командами и ожидаемым временем.

**Направление 2 — сценарии для специалистов:** заранее подготовленные **промпты / чеклисты** под роли в Cursor — чтобы не изобретать формулировку каждый раз. Пример: архитектор → аудит; разработчик → уровни тестирования после правки.

## Часть A · Уровни запуска тестов (черновик)

| Уровень | Когда | Состав (черновик) | Цель по времени |
|---------|--------|-------------------|-----------------|
| **L0 · smoke** | После каждой осмысленной правки; перед коммитом в feature-ветку | Минимальный набор: 1–2 Vitest по затронутому файлу; 1 PHPUnit `--filter` по модулю; **без E2E** по умолчанию | **&lt; 2–5 мин** |
| **L1 · адресный (targeted)** | PR / перед merge; затронут модуль или зона Pro/Client | Все тесты **тега/папки/файла** изменений; E2E **одного потока** (grep/spec по модулю) | **&lt; 15–25 мин** |
| **L2 · модульный** | Закрытие тикета; приёмка модуля | Весь сьют модуля (PHP feature + TS unit + E2E flow модуля) | **&lt; 30–45 мин** |
| **L3 · полный (regression)** | Перед prod / конец спринта / «прогони тесты» по регламенту | `npm run test:ts` + `php artisan test` + `npm run test:e2e` (стек поднят) | **как сейчас** |

**Принципы:**

- Уровень **не ниже**, чем требует риск изменения (auth/billing/partner → минимум L1).
- **E2E** — самый дорогой слой; в L0/L1 только по карте «модуль → spec».
- Карта «**изменил X → гони Y**» — отдельный артеfact (таблица или `docs/Техдок/…`), не только в голове.
- В `package.json` / composer — **именованные скрипты** (`test:smoke`, `test:module:scheduling`, …) — *идея, не реализовано*.

**Примеры команд (существующие building blocks):**

```bash
# L0 — пример после правки scheduling API
docker compose exec -u sail -T laravel.test php artisan test --filter=SchedulingApiTest

# L1 — пример E2E одного потока
docker compose exec -u sail -T laravel.test npm run test:e2e -- e2e/pro-workouts.flow.spec.ts

# L3 — полный (канон qa-test-runs)
docker compose exec -u sail -T laravel.test npm run test:ts
docker compose exec -u sail -T laravel.test php artisan test
docker compose exec -u sail -T laravel.test npm run test:e2e
```

## Гипотеза

Если зафиксируем **уровни L0–L3** + **именованные npm/artisan-скрипты** + **промпты по ролям**, то:

- время обратной связи на D-неделе **сократится** (чаще L0 вместо L3);
- полный L3 **не потеряется** перед релизом;
- агенты перестанут «всегда гонять всё» или «не гонять ничего».

**Как проверим:** 2–3 спринта — замер «время от правки до green» на типовых тикетах; число регрессий, пойманных только на L3.
