## Суть

Клиент описывает блюдо **текстом** в приёме пищи (домашняя еда, кафе без этикетки). Текст уходит на **сервер**, обрабатывается **LLM**, возвращается **оценка КБЖУ с диапазоном погрешности** (min/max), а не одна «точная» цифра. Клиент принимает или правит вручную.

Дополняет штрихкод — не заменяет: не всё можно просканировать.

## Зачем / для кого

- **Клиент** — не считать калории вручную для «гречка с котлетой», «суп бабушки».
- **Тренер** — структурированный ориентир в ленте приёмов; видно, что цифра **оценочная**, не с этикетки.

## UX (канон идеи)

1. Клиент пишет описание приёма (как сейчас) или нажимает **«Оценить КБЖУ»**.
2. Подсказка: указать **граммы, способ готовления, масло/соус** — точность выше.
3. Запрос **только онлайн**; офлайн — сохранить текст, оценить при sync.
4. Ответ: диапазон, напр. **~350–500 ккал**, Б/Ж/У min–max, список **допущений** («курица ~150 г, если не указано»).
5. Кнопки: **«Принять»** / **«Править вручную»**.
6. В ленте тренера — пометка **«оценка ИИ»**, не смешивать с данными штрихкода.

Позиционирование: **«умная оценка для ориентира»**, не медицинский расчёт.

## Архитектура (черновик)

```text
Client: text в nutrition_meals
    → POST /api/v1/nutrition/meals/{id}/estimate-kbju
        → Laravel: промпт + structured JSON от LLM (только сервер)
    ← { kcal_min, kcal_max, protein_min, protein_max, …,
         confidence, assumptions[], kbju_source: "ai_estimate" }
Client: показ диапазона → принять / править
```

**Не из браузера** — ключи API и политика ПДн на бэкенде.

Опционально позже: **фото приёма + текст** (vision) — точнее, дороже; в MVP идеи достаточно текста.

## Данные

Те же поля КБЖУ в `nutrition_meals`, что и в [штрихкод-идее](дневник-питания-штрихкод-кбжу.md), плюс для ИИ:

| Поле | Назначение |
|------|------------|
| `kbju_source` | `ai_estimate` |
| `kcal_min`, `kcal_max`, … | диапазоны по макронутриентам |
| `ai_confidence` | low / medium / high (опц.) |
| `ai_assumptions` | json/text — что модель додумала |

Один приём — **один источник** КБЖУ: штрихкод **или** ручной **или** ИИ, не смешивать без явного действия пользователя.

## Риски

| Риск | Митигация |
|------|-----------|
| Погрешность ±30–50% при размытом описании | Диапазон, допущения, подсказки при вводе |
| ПДн: текст еды → внешний LLM | Согласие, выбор провайдера, юрист; минимум логов |
| Стоимость API | Квоты по тарифу (Лайт / Профи) |
| Клиент «подгоняет» описание | Честные диапазоны, дисклеймер в UI |
| Офлайн PWA | Оценка только online; текст в outbox как сейчас |

## Ограничения MVP идеи

- Только **текст** (без vision в первой версии).
- Без целей тренера «съешь N ккал» и без аналитики трендов.
- Без уточняющего диалога с ИИ в v1 (можно во v2: «масло добавляли?»).

Оценка реализации: **~20–28 ч** (API, промпт, structured output, UI диапазона, дисклеймеры, тесты) — после общих полей КБЖУ из штрихкод-линейки.

## Юридическое и тариф

- Дневник — мед. контур in-app; **трансграничная передача текста в LLM** — отдельная строка в политике / согласии.
- Тариф: лимит **запросов ИИ в день/месяц** на Лайте ([L-11 в сборнике](../бэклог/T-078-идеи-ограничения-тарифа-профи.md)).

## Гипотеза

Если клиент получает ориентир по КБЖУ для домашней еды без ухода в сторонние калькуляторы, выше полнота дневника; проверка — доля приёмов с `ai_estimate` и обратная связь тренеров на пилоте.
